# Спецификация системы передачи телеметрии с дедупликацией (Telemetry Deduplication Link)

## 1. Общие сведения и архитектура системы

TDL собирает телеметрию с датчиков, подключенных к передатчикам по I²C, и передает ее удаленному приемнику. Передатчик опрашивает до четырех датчиков, преобразует результаты измерений в 32-битные слова и помещает их во входное FIFO. Дедупликация сокращает объем повторяющихся данных перед передачей по однобитному SDR-каналу. Физический уровень канала не входит в эту спецификацию; для аппаратной реализации рассматривается LVDS.

Система рассчитана на работу в условиях, когда скорость поступления измерений может быть выше скорости канала до приемника. FIFO временно сглаживает эту разницу, а при заполнении передатчик приостанавливает опрос датчиков до освобождения места. Дедупликация увеличивает время до заполнения FIFO, когда измерения повторяются, но не гарантирует передачу произвольного потока без ограничения скорости опроса.

| `SYS_CLK_HZ` | `integer` | — | `50_000_000` | Частота системного тактового сигнала передатчика (50 МГц). |
| `VAL_FIFO_DEPTH` | `integer` | `8 .. 64` | `16` | Глубина промежуточного буфера валидации CRC в приемнике. |
| `RX_FIFO_DEPTH` | `integer` | `8 .. 64` | `16` | Глубина буфера декодированных слов на канале приемника. |

## 3. Интерфейсы и сигналы модулей

### 3.1. Модуль Передатчика (`tdl_tx_top`)

Содержит входное FIFO, ассоциативный словарь, таблицы статистики (CMS/BF/LRU/Clock), регистры конфигурации и FSM кодера.

| Сигнал | Направление | Разрядность | Описание |
| --- | --- | --- | --- |
| `clk` | Вход | 1 bit | Основной тактовый сигнал. |
| `rst_n` | Вход | 1 bit | Активный низкий сигнал сброса. |
| **Поток телеметрии во входной FIFO (AXI4-Stream):** | | | |
| `s_axis_tdata` | Вход | `DATA_WIDTH` | Сформированное 32-битное слово телеметрии. Формат зависит от выбранных датчиков и задается отдельно. |
| `s_axis_tvalid` | Вход | 1 bit | Строб валидности входного слова. |
| `s_axis_tready` | Выход | 1 bit | Готовность FIFO принять слово; при заполнении FIFO сигнал снимается. |
| `s_axis_tlast` | Вход | 1 bit | Признак конца пакета/набора данных; при непрерывном опросе датчиков может не использоваться. |
| **Интерфейс датчиков I²C:** | | | |
| `i2c_scl` | Двунаправленный, открытый сток | 1 bit | Тактовая линия общей I²C-шины передатчика; входное состояние используется для clock stretching. |
| `i2c_sda` | Двунаправленный, открытый сток | 1 bit | Линия данных общей I²C-шины передатчика. |
| **Межчиповый канал связи (SDR 1-bit Выход):** | | | |
| `sdr_data` | Выход | 1 bit | 1-битная SDR-шина данных и заголовков кадров дедупликации. |
| `sdr_clk` | Выход | 1 bit | Тактовый сигнал SDR-шины. |
| `sdr_ready` | Вход | 1 bit | Сигнал готовности приемника принять очередной бит; при `0` передатчик удерживает текущий бит. |
| **Интерфейс управления SPI Slave:** | | | |
| `spi_sclk` | Вход | 1 bit | Тактовый сигнал SPI. Данные MOSI принимаются по переднему фронту, MISO изменяется по заднему фронту (CPHA=0). |
| `spi_cs_n` | Вход | 1 bit | Низкоактивный выбор SPI-устройства. При `1` выход `spi_miso` переводится в третье состояние. |
| `spi_mosi` | Вход | 1 bit | Последовательные команды, адреса и данные от ведущего SPI. Передача выполняется MSB. |
| `spi_miso` | Выход | 1 bit | Последовательные данные чтения регистра, передаваемые ведомым SPI. |
| `spi_irq` | Выход | 1 bit | Сигнал прерывания. |

#### Опрос датчиков

Передатчик последовательно опрашивает до четырех датчиков на общей I²C-шине. Для каждого датчика задается 7-битный адрес. Опрос выполняется циклически; конкретные команды чтения, регистры датчика, формат измерения и упаковка результата в 32-битное слово определяются после выбора модели датчика. Контроллер поддерживает номинальные режимы около 100 кГц и 400 кГц; выбранная частота не должна превышать ограничение самого медленного подключенного датчика.

При NACK или таймауте передатчик фиксирует соответствующий статус, может сформировать прерывание, завершает текущую транзакцию и переходит к следующему разрешенному датчику. При ошибке или зависании шины контроллер фиксирует `I2C_BUS_ERR`, выполняет восстановление шины и затем возобновляет цикл опроса. Адреса датчиков должны быть уникальны на одной шине; если выбранные устройства имеют одинаковые адреса, потребуется дополнительное аппаратное решение (например, мультиплексор), которое в этой спецификации не задается.

Коррекция погрешности или удаление младших разрядов измерения на уровне PHY может быть добавлена после выбора датчиков. В данной спецификации слова дедуплицируются только при точном совпадении всех 32 бит.

#### Интерфейс телеметрийного канала

Логический канал передает `sdr_data` синхронно с `sdr_clk`. Физическая реализация линии, электрические уровни, кабель и зависимость допустимой скорости от длины линии определяются отдельно. Делитель SDR позволяет задавать режимы передачи и исследовать влияние пропускной способности на заполнение FIFO.

### 3.2. Модуль Приемника (`tdl_rx_top`)

Содержит $N$ независимых декодеров каналов, $N$ буферов валидации CRC, аппаратный обработчик ошибок, блок CSR и арбитр AXI4-Stream. Передача данных управления и сообщений прерываний (MSI) между ЦПУ и приемником выполняется по 32-битному пакетному интерфейсу `iolink`.

| Сигнал | Направление | Разрядность | Описание |
| --- | --- | --- | --- |
| `clk` | Вход | 1 bit | Основной тактовый сигнал приемника. |
| `rst_n` | Вход | 1 bit | Активный низкий сигнал сброса. |
| **Входные межчиповые каналы SDR ($N \times$ 1 bit):** | | | |
| `sdr_data` | Вход | `NUM_CHANNELS` | Вектор 1-битных SDR-шин данных от $N$ передатчиков. |
| `sdr_clk` | Вход | `NUM_CHANNELS` | Вектор тактовых сигналов SDR-шин от $N$ передатчиков. |
| `sdr_ready` | Выход | `NUM_CHANNELS` | Вектор сигналов готовности принять очередной бит (обратное давление на каналы SDR). |
| **Интерфейс к ЦПУ / DMA / SoC (AXI4-Stream Выход):** | | | |
| `m_axis_out_tdata` | Выход | `DATA_WIDTH` | Восстановленное 32-битное значение данных. |
| `m_axis_out_tid` | Выход | 8 bits | Идентификатор источника/канала (`Sensor_ID`). |
| `m_axis_out_tvalid` | Выход | 1 bit | Флаг готовности декодированного слова для ЦПУ/DMA. |
| `m_axis_out_tready` | Вход | 1 bit | Сигнал готовности ЦПУ/DMA к приему слова. |
| `m_axis_out_tlast` | Выход | 1 bit | Признак последнего слова в блоке/пакете данных. |
| **Интерфейс управления и MSI (32-bit `iolink`):** | | | |
| *Канал Запросов ЦПУ $\rightarrow$ Приемник (Downstream Request):* | | | |
| `iolink_rx_val` | Вход | 1 bit | Строб валидности данных/пакета запроса от ЦПУ. |
| `iolink_rx_data` | Вход | 32 bits | 32-битная шина данных запроса (Header, Address, Write Data). |
| `iolink_rx_rdy` | Выход | 1 bit | Сигнал готовности `iolink_rx` модуля к приему данных от ЦПУ. |
| *Канал Ответов и MSI Приемник $\rightarrow$ ЦПУ (Downstream Completion & Interrupts):* | | | |
| `iolink_tx_val` | Выход | 1 bit | Строб валидности данных/пакета ответа или MSI от приемника. |
| `iolink_tx_data` | Выход | 32 bits | 32-битная шина данных ответа (Header, Completion, Read Data, MSI Vector). |
| `iolink_tx_rdy` | Вход | 1 bit | Сигнал готовности ЦПУ к приему ответов и MSI-сообщений. |

## 4. Протоколы передачи

### 4.1. Формат кадров от передатчика приемнику

Данные по 1-битной шине передаются пакетами переменной длины. Тип пакета определяется старшим байтом-заголовком (Preamble Header):

```text
1. RAW-кадр (обычный):          [ 0xA1 (Header) ] [ Byte 3 ] [ Byte 2 ] [ Byte 1 ] [ Byte 0 ]
2. KEY-кадр (сжатый):           [ 0xB2 (Header) ] [ Key (8-bit) ]
3. SYNC-кадр (обновление):      [ 0xC3 (Header) ] [ Key (8-bit) ] [ Byte 3 ] [ Byte 2 ] [ Byte 1 ] [ Byte 0 ]
4. CRC-кадр (контроль):         [ 0xD4 (Header) ] [ CRC-8 Payload ]

```

| Заголовок | Тип кадра | Длина пакета | Назначение |
| --- | --- | --- | --- |
| `0xA1` | **`HEADER_RAW`** | 5 байт | Передача полных 32-битных данных без изменения словаря. |
| `0xB2` | **`HEADER_KEY`** | 2 байта | Передача 8-битного ключа при совпадении со словарем. |
| `0xC3` | **`HEADER_SYNC`** | 6 байт | Запись/обновление пары «Ключ-Значение» в словаре. |
| `0xD4` | **`HEADER_CRC`** | 2 байта | Проверка накопленной контрольной суммы блока данных (Block/Idle CRC). |

При CRC_MODE = 10 (Continuous Mode) в регистре CRC_CFG_REG (см. пункт 6.2) к `HEADER_RAW`, `HEADER_KEY` и `HEADER_SYNC` в конец добавляется байт CRC-8

Каждый байт передается последовательно, начиная со старшего бита. `sdr_clk` удерживается в низком уровне вне передачи и формирует тактовые импульсы только для приема битов: при `sdr_ready = 1` принимается один бит на такт, а при `sdr_ready = 0` тактирование приостанавливается и передатчик удерживает текущий бит. Переход к следующему байту выполняется только после передачи всех восьми бит текущего байта.

### 4.2. Протокол управления `iolink` (32-bit Stream)

Межчиповый/внутричиповый интерфейс управления `iolink` представляет собой симметричный потоковый протокол («точка-точка») с управлением потоком `val / data[31:0] / rdy`. Каждое логическое обращение состоит из последовательной передачи 32-битных слов за несколько тактов.

#### **Структура первого сообщения (Header Word, 32 bit)**

Все управляющие флаги и параметры транзакции упакованы в первое 32-битное слово пакета:

```text
 31      28 27          20 19      16 15      12 11       8 7          0
┌──────────┬──────────────┬──────────┬──────────┬──────────┬────────────┐
│  OPCODE  │  REQUEST_ID  │   SIZE   │  STATUS  │    BE    │  RESERVED  │
│ (4 bits) │   (8 bits)   │ (4 bits) │ (4 bits) │ (4 bits) │  (8 bits)  │
└──────────┴──────────────┴──────────┴──────────┴──────────┴────────────┘

```

##### **Описание полей заголовка (`Header[31:0]`)**

* **`OPCODE` (4 бита):** Код операции транзакции.
* **`REQUEST_ID` (8 бит):** Идентификатор транзакции (Tag). Узел-инициатор генерирует ID, узел-исполнитель **обязан скопировать** его в ответный пакет (`READ_RESP` / `WRITE_RESP`).
* **`SIZE` (4 бита):** Размер передаваемого блока данных.
* **`STATUS` (4 бита):** Статус выполнения транзакции (заполняется в ответах `RESP`):
  * `0x0` — **`OKAY`**: Транзакция выполнена успешно.
  * `0x1` — **`DECERR`**: Ошибка декодирования (обращение по несуществующему адресу).
  * `0x2` — **`HW_ERR`**: Фатальный аппаратный сбой (ошибка CRC, таймаут валидации, сбой BRAM).

* **`BE` (Byte Enable) [11:8] (4 бита):** Маска валидных байт в слове данных (`be[3:0]`).
* **`RESERVED` [7:0] (8 бит):** Зарезервировано (заполняется нулями).

---

#### **Поддерживаемые коды операций (`OPCODE`)**

Интерфейсы `iolink` со стороны ЦПУ и Приемника полностью равноправны и используют единый набор команд:

| `OPCODE` | Мнемоника | Данные в пакете | Описание транзакции |
| --- | --- | --- | --- |
| `0x1` | **`READ_REQ`** | Без данных | Запрос на чтение регистра. Последовательность: Header $\rightarrow$ Address. |
| `0x2` | **`WRITE_REQ`** | С данными | Запрос на запись с подтверждением. Последовательность: Header $\rightarrow$ Address $\rightarrow$ Write Data. |
| `0x3` | **`POSTED_WRITE`** | С данными | Запись без ожидания подтверждения (без ответа). Последовательность: Header $\rightarrow$ Address $\rightarrow$ Write Data. |
| `0x8` | **`READ_RESP`** | С данными | Ответ на запрос чтения. Содержит `REQUEST_ID` запроса и `STATUS`. Последовательность: Header $\rightarrow$ Read Data. |
| `0x9` | **`WRITE_RESP`** | Без данных | Подтверждение выполнения записи (`WRITE_REQ`). Содержит `REQUEST_ID` и `STATUS`. Последовательность: Header. |

---

#### **Диаграммы транзакций**

Поток данных передается стробом `val` при наличии готовности `rdy` принимающей стороны.

##### 1. Чтение регистра (ЦПУ $\leftrightarrow$ Приемник)

```text
Инициатор (ЦПУ):
  Такт 1: Header [READ_REQ, ReqID=0x12, SIZE=0, BE=0xF]
  Такт 2: Address [32'h0000_0010] (Регистр CNT_TOTAL_DECODED)

Исполнитель (Приемник):
  Такт 1: Header [READ_RESP, ReqID=0x12, SIZE=1, Status=OKAY]
  Такт 2: Read Data [32'h0000_A12F] (Значение счетчика)

```

##### 2. Запись в регистр CSR (ЦПУ $\leftrightarrow$ Приемник)

```text
Инициатор (ЦПУ):
  Такт 1: Header [WRITE_REQ, ReqID=0x13, SIZE=1, BE=0xF]
  Такт 2: Address [32'h0000_0000] (Регистр RX_GLOBAL_CTRL)
  Такт 3: Write Data [32'h0000_0001] (Данные: RX_EN=1)

Исполнитель (Приемник):
  Такт 1: Header [WRITE_RESP, ReqID=0x13, SIZE=0, Status=OKAY]

```

##### 3. Генерация MSI-прерывания (Приемник $\leftrightarrow$ ЦПУ)

При возникновении ошибки CRC или таймаута Приемник выступает в роли инициатора транзакции записи в системный контроллер прерываний ЦПУ:

```text
Инициатор (Приемник):
  Такт 1: Header [WRITE_REQ, ReqID=0x80, SIZE=1, BE=0xF]
  Такт 2: Address [32'hFEE0_0000] (Системный адрес MSI вектора)
  Такт 3: Interrupt Data [32'h0000_0001] (Payload: CRC Error Ch0)

Исполнитель (ЦПУ):
  Такт 1: Header [WRITE_RESP, ReqID=0x80, SIZE=0, Status=OKAY]

```

### 4.3 Протокол управления `SPI`

Регистры передатчика доступны через встроенный SPI Slave. Каждая транзакция
начинается с установки `spi_cs_n = 0` и состоит из командного байта и байта данных.
Командный байт:

```text
 7       6                 1   0
┌────────┬─────────────────┬───┐
│RESERVED│      ADDR       │R/W│
│ [7]    │     [6:1]       │   │
└────────┴─────────────────┴───┘
```

* `ADDR[6:1]` — 6-битный байтовый адрес регистра из карты раздела 6.2 (`0x00 .. 0x3F`).
* `R/W = 1` — чтение регистра; `R/W = 0` — запись регистра.
* При записи второй байт содержит `DATA[7:0]`. Запрос к регистровому блоку формируется после приема всех восьми бит.
* При чтении второй байт передается ведущим SPI (обычно `0x00`), а ведомый возвращает `DATA[7:0]`.
* `spi_cs_n` должен оставаться в нуле на протяжении обоих байтов. Возврат `spi_cs_n` в единицу завершает транзакцию и сбрасывает состояние SPI-доступа.
* Запись выполняется только после полного приёма байта данных. Доступ к адресу вне карты фиксирует `SPI_ADDR_ERR`. Сигнал `spi_irq` зависит от маски `INT_ENABLE_REG`.
* SPI использует mode 0. Высокая и низкая фазы SCLK, интервалы установки и удержания CS относительно первого и последнего подъёмов SCLK и пауза между транзакциями составляют не менее четырёх периодов `clk`. При `clk=50 МГц` симметричный SCLK ограничен 6,25 МГц. Мастер выставляет MOSI в начале низкой фазы и удерживает его до конца высокой.
* CSR-доступ для чтения выполняется после приёма команды. При обрыве байта ответа уже принятый доступ сохраняется. Для чтения за пределами карты второй байт равен `0x00`.

## 5. Алгоритм работы и внутренняя логика

### 5.1. Логика Передатчика (`tdl_tx_top`)

#### 1 **Опрос датчиков и прием данных**

I²C Master циклически опрашивает разрешенные датчики и преобразует каждый результат в 32-битное слово согласно профилю датчика. Сформированное слово передается во входное FIFO интерфейсом AXI4-Stream: запись выполняется при `s_axis_tvalid && s_axis_tready`. Формат слова определяется выбранной моделью датчика и не фиксируется этой спецификацией.

Когда FIFO заполнено, `s_axis_tready` снимается и опрос приостанавливается до освобождения места. Условие полного FIFO видно в `STATUS_REG`. Переход в full устанавливает `FIFO_OVERFLOW` в `INT_STATUS_REG`, а маска разрешает вывод события на `spi_irq`. После появления свободного места циклический опрос продолжается. Датчик опрашивается, когда входное FIFO может принять новое слово.

#### 2 **Анализ трафика (Encoder FSM)**

Controller захватывает слово при разрешённой обработке и готовности backend, фиксирует настройки и выполняет exact lookup, если Bypass выключен. Hit даёт KEY. Miss Clock/LFU/SLRU даёт SYNC по правилам соответствующей policy. TinyLFU применяет BF/CMS admission и может выдать RAW; Bypass всегда выдаёт RAW.

Dictionary и metadata обновляются на приёме descriptor буфером (commit), а не на завершении SDR; порядок SYNC→KEY сохраняется. Нормативные правила — §8.2 и §8.9.

#### 3 **Контроль CRC**

Параллельно с передачей байт кадра аппаратный блок CRC8 вычисляет накопительную контрольную сумму. По паузе в FIFO или по достижению порога переданных слов ($M$) FSM внедряет кадр `HEADER_CRC` (`0xD4`).

#### 4 **Смена конфигурации**

Настройки CRC согласуются между TX/RX. Алгоритмические настройки являются TX-local; порядок изменения задан в §6.1.1, формат снимка — в §8.10.

### 5.2. Логика Приемника (`tdl_rx_top`)

#### 1 **Декодирование и Буфер Валидации**

* Приемник содержит $N$ экземпляров модуля `DEDUPLICATOR_RX_CHANNEL`.
* При получении `HEADER_RAW`: Собирает 4 байта и отправляет 32-битное слово в Буфер Валидации.
* При получении `HEADER_SYNC`: Записывает `Value` по адресу `Key` в **свой** словарь и отправляет 32-битное слово в Буфер Валидации.
* При получении `HEADER_KEY`: За **1 такт** извлекает значение из **своего** словаря `dictionary[Key]` и отправляет его в Буфер Валидации.
* Восстановленные слова в **Буфере Валидации (Validation FIFO)** данного канала удерживаются там до тех пор, пока не придет `HEADER_CRC`, если включены соответсвующие настройки.

#### 2 **Проверка CRC**

* При получении кадра `HEADER_CRC` (`0xD4`) приемник сравнивает переданный CRC-8 с аппаратно рассчитанным значением по принятым байтам.
* **CRC совпал:** Данные из буфера валидации переливаются в канальное FIFO и становятся доступны арбитру AXI.
* **CRC НЕ совпал:** Включается аппаратный `ERROR_HANDLER`: данные в буфере валидации маркируются как недействительные и сбрасываются, запись битых ключей в словарь блокируется, взводится линия прерывания `rx_irq`.

#### 3 **Арбитраж**

* Каждое канальное FIFO хранит декодированные 32-битные слова.
* Модуль `AXI_ARBITER` опрашивает канальные FIFO по круговому алгоритму (Round-Robin).
* При наличии данных арбитр забирает слово, выставляет его на выходную шину `m_axis_out_tdata`, а на шину `m_axis_out_tid` выставляет индекс канала (`Sensor_ID`), пропуская данные в ЦПУ.

### 5.3. Скорость канала и накопление телеметрии

Параметр `SDR_CLK_DIV` задает частоту передачи от системного тактового сигнала 50 МГц. При фиксированном составе кадров снижение `F_SDR` уменьшает скорость опустошения входного FIFO. При повторяющихся 32-битных словах дедупликация передает короткие KEY-кадры после заполнения словаря и снижает средний объем трафика. Для уникальных или быстро меняющихся измерений доля RAW/SYNC-кадров возрастает, поэтому дедупликация имеет конечный предел эффективности.

Если средняя скорость поступления измерений с учетом результата дедупликации превышает пропускную способность SDR-канала, FIFO заполняется и опрос датчиков приостанавливается до освобождения места. Подбор делителя позволяет исследовать эту границу для разных потоков данных; расстояние до приемника само по себе в RTL не измеряется и не используется для автоматической регулировки частоты.

## 6. Карта регистров управления и состояния Передатчика (`tdl_tx_top`)

Управление регистрами передатчика `tdl_tx_top` осуществляется по интерфейсу
**SPI Slave**. Адресация байтовая, адрес занимает 6 бит.

---

### 6.1. Классификация регистров по способу синхронизации и считывания

Регистры передатчика разделены на три строго изолированные группы:

#### 6.1.1. TX-Local регистры и границы применения

TX-Local означает отсутствие необходимости повторять настройку на RX; это не означает изменение уже обрабатываемого слова сразу после SPI-записи.

`TX_EN=0` запрещает новые захваты и подъёмы SDR; начатая высокая фаза завершается, принятые слова/кадры не отменяются. Bypass фиксируется на захвате каждого слова. Policy использует неизменяемый снимок настроек для принятой транзакции.

ALGO_SEL и SLRU_CFG_REG задаются до первого захвата после reset и удерживаются до reset. Активные значения фиксируются; runtime запись не запускает миграцию. Изменение после начала работы не поддерживается, выявляется assertion в интеграции и не меняет активный алгоритм/квоты.

Для изменения `BF_EN`, `CU_DISABLE`, `AGING_DISABLE` и двух байтов `AGING_PERIOD` во время работы TinyLFU ПО выполняет следующую последовательность.

1. Останавливает подачу новых слов и даёт завершиться handshake уже выставленного `tvalid`. Оставляет `TX_EN=1`, чтобы контроллер и сериализатор могли продолжать работу.
2. Опрашивает `STATUS_REG` (`0x07`) до чтения, в котором одновременно `IN_FIFO_EMPTY=1` и `FSM_STATE=0` (`IDLE`). Условие для байта статуса — `(status & 0xE1) == 0x01`. Если истёк таймаут опроса, ПО завершает попытку с прежними `TX_EN` и настройками. Длительность опроса зависит от backpressure на SDR.
3. От завершения успешного чтения ждёт не менее `TINYLFU_IDLE_WAIT_CYCLES=518` периодов `clk`. При 50 МГц это 10,36 мкс. ПО рассчитывает паузу по минимальной рабочей частоте `clk` и округляет её вверх до разрешения своего таймера.
4. Сохраняя остановку источника, снимает `TX_EN`, записывает новые поля и оба байта периода, затем возвращает `TX_EN=1` и возобновляет подачу слов. При записи `MODE_REG` сохраняет `ALGO_SEL`.

При остановленном источнике успешное чтение статуса подтверждает, что все захваченные слова уже прошли commit. Пауза покрывает вторую запись BF, запуск обслуживания, 512 тактов прохода CMS и возврат готовности через FSM. Ротация BF занимает до 128 тактов и идёт параллельно с проходом CMS при включённом aging. Для первоначальной настройки до первого `word_take` ПО записывает значения при `TX_EN=0`.

Очередь и активный SDR-кадр сохраняются при остановке TX. При полном frame buffer преждевременное снятие `TX_EN` может остановить сериализатор и задержать `desc_ready`, поэтому ПО начинает опрос с включённым TX. Следующее захваченное слово получает полный снимок новых настроек. Новый `AGING_PERIOD` начинает новый интервал (§8.3.4). BF при выключении замораживается и при включении продолжает сохранённую историю.

SOFT_RESET, ручная очистка и команды — расширение системы; в базовой реализации отключены (§8.11).

#### 6.1.2. Настройки формата канала и синхронизация ЦП

CRC_CFG_REG требует согласованной настройки TX/RX программным протоколом. MODE_REG задаёт TX-local политику выбора записей и не меняет формат RAW/KEY/SYNC. RX не повторяет replacement policy, поэтому MODE_REG не относится к In-Band Sync.

Для будущих команд очистки требуется протокол сохранения соответствия используемых ключей и порядка кадров. LFU/SLRU/Clock/BF/CMS metadata существуют на TX, RX содержит отображение ключ→слово. Очистка RX через CH_CTRL не является очисткой metadata TX policy.

#### 6.1.3. Read-Shadowed Регистры

32-битные счетчики метрик, требующие фиксации чтения (Latch-on-Read) во избежание состояния гонки. При чтении по адресу младшего байта счетчика (например, `0x0C` для `CNT_TOTAL_WORDS`) SPI-доступ фиксирует все 32 бита текущего счетчика в теневой буфер чтения `shadow_rd_reg[31:0]`. Последующие чтения адресов `0x0D`, `0x0E`, `0x0F` выдают байты из зафиксированного `shadow_rd_reg`.

```text
    ТЕНЕВОЕ ЧТЕНИЕ (Read-Shadowing / Latch-on-Read для 32-битных счетчиков):
    Чтение SPI (Byte 0) ──► Фиксация 32-бит счетчика в shadow_rd_reg[31:0]
                            ├─► Возврат Byte 0
    Чтение SPI (Byte 1) ───► Возврат shadow_rd_reg[15:8]   (Без состояния гонки)
    Чтение SPI (Byte 2) ───► Возврат shadow_rd_reg[23:16]
    Чтение SPI (Byte 3) ───► Возврат shadow_rd_reg[31:24]

```

---

Пять счётчиков CNT_TOTAL_WORDS, CNT_KEY_FRAMES, CNT_RAW_FRAMES, CNT_SYNC_FRAMES и CNT_BF_FILTERED обнуляются общим reset и насыщаются на 0xFFFFFFFF. HIGH_HIT_RATE использует условие total != 0 и строгое сравнение 255 × key > threshold × total с произведениями шириной не менее 40 бит. Условие является уровнем установки sticky-статуса. При одновременном W1C и новом событии установка события имеет приоритет.

Снимок реализован генерируемой буферизацией чтения по младшему байту. Подробные контракты приведены в [tdl_tx_stats](modules/transmitter/tdl_tx_stats.md), [tdl_tx_reg_bridge](modules/transmitter/tdl_tx_reg_bridge.md) и [tx_regs](modules/transmitter/tx_regs.md).

#### `SDR_CLK_DIV` — делитель SDR

`SDR_CLK_DIV` — 16-битное беззнаковое значение `D`, записываемое младшим байтом по `0x20`, старшим по `0x21`. При системной частоте `F_SYS = 50 МГц` выходная частота задается формулой:

```text
F_SDR = F_SYS / (2 × (D + 1))
```

Один бит передается на активном фронте `sdr_clk`; таким образом, номинальная скорость канала в битах в секунду равна `F_SDR`. Значение `D = 0` задает максимальную частоту 25 МГц, `D = 65535` — приблизительно 381,5 Гц. Промежуточные частоты доступны с дискретностью делителя. Делитель применяется к последующим передачам; если запись сделана во время кадра, новое значение вступает в силу после его завершения.

Этот широкий диапазон предназначен для проверки работы кодера, FIFO и дедупликации при разных скоростях канала. Он не задает фактическую скорость для конкретной длины кабеля или физического интерфейса.

### 6.3. Детализация ключевых регистров Передатчика

#### `0x00` — `CTRL_REG` (Control Register)

* `Bit [0]` — **`TX_EN`**: Включение передатчика (`1` — активен, `0` — заблокирован). Применимо немедленно.
* `Bit [1]` — **`BYPASS_EN`**: Режим сквозной передачи без дедупликации.
* `Bit [2]` — **`SOFT_RESET`**: Программный сброс FSM и FIFO передатчика. Применяется немедленно и сбрасывает текущий пакет.
* `Bits [7:3]` — Зарезервировано.

#### `0x01` — `MODE_REG` (Algorithm Selection — TX-Local)

* `Bits [1:0]` — **`ALGO_SEL`**:
* `00` — **TinyLFU + CU-CMS** (Основной режим: 2×BF + CU-CMS + Затухание).
* `01` — **Segmental LRU (SLRU / 2Q)** (Двухсегментная очередь).
* `10` — **Clock / CAR** (Простой кольцевой алгоритм замещения с флагами).
* `11` — **Pure LFU** (Вытеснение по локальной статистике использования).

* `Bit [2]` — **`CU_DISABLE`**: Отключение Conservative Update (`1` — переключение в стандартный режим CMS).
* `Bit [3]` — **`AGING_DISABLE`**: Отключение деления CMS и local counters TinyLFU на 2. BF rotation этим битом не отключается; LFU, SLRU и Clock aging не используют.
* `Bits [7:4]` — Зарезервировано.

#### `0x04` — `BF_CTRL_REG` (Bloom Filter Control)

* `Bit [0]` — **`BF_EN`** *(R/W)*: Включение фильтрации одноразовых слов через фильтры Блума (`1` — включено).
* `Bit [1]` — **`FORCE_ROTATE`** *(WO Strobe, Self-Clearing)*: Запрос ротации/очистки BF. В базовой версии аппаратное действие отключено (§8.11); однократный строб не задаёт длительность очистки.
* `Bit [2]` — **`BF_RESET`** *(WO Strobe, Self-Clearing)*: Запрос очистки обоих поколений BF. В базовой версии аппаратное действие отключено (§8.11).
* `Bits [7:3]` — Зарезервировано.

#### `0x05` — `SLRU_CFG_REG` (TX-Local)

`[7:0]` задаёт вместимость Probationary: `N_prob`, `N_prot=DICT_SIZE-N_prob`. Допустимо `1 <= N_prob < DICT_SIZE`. Reset `0x40` сохраняется; при `DICT_SIZE<=64` software должно записать допустимое значение до запуска SLRU. Это квота, а не граница физических ключей. Неверное значение блокирует SLRU через `cfg_valid=0` без clamp (§8.4, §8.10).

#### `0x06` — `CMD_REG` (Command Register — WO Strobes, Auto-Clearing)

* `Bit [0]` — **`FLUSH_DICT_CMD`**: Запрос принудительной очистки словаря передатчика. Передатчик дожидается паузы, очищает свой словарь и сбрасывает `FLUSH_BUSY` = 0. Для очистки словарей приемника ЦП отдельно задает `FLUSH_CH_DICT` в `CH_CTRL` нужных каналов.

* `Bit [1]` — **`CLR_COUNTERS_CMD`**: Однотактный импульс сброса всех счетчиков производительности.

* `Bits [7:2]` — Зарезервировано.

#### `0x07` — `STATUS_REG` (Status Register — Read Only)

* `Bit [0]` — **`IN_FIFO_EMPTY`**: Входное FIFO пусто.
* `Bit [1]` — **`IN_FIFO_FULL`**: Входное FIFO переполнено.
* `Bit [2]` — Зарезервировано.
* `Bit [3]` — **`FLUSH_BUSY`**: `1` — идет очистка словаря передатчика (программное обеспечение должно ожидать `0`).
* `Bit [4]` — **`RESET_BUSY`**: `1` — идет процесс аппаратного сброса/инициализации BRAM.
* `Bits [7:5]` — **`FSM_STATE`**: Текущий код состояния кодера.

#### `0x08` / `0x09` — `INT_ENABLE_REG` & `INT_STATUS_REG` (Interrupt Control)

* `Bit [0]` — **`FIFO_OVERFLOW`**: Прерывание по переполнению входного FIFO.
* `Bit [1]` — Зарезервировано.
* `Bit [2]` — **`AGING_EVENT`**: Событие завершения запрошенной ротации Блума, деления счётчиков или обеих операций TinyLFU.
* `Bit [3]` — **`HIGH_HIT_RATE`**: Прерывание при превышении порога коэффициента дедупликации, заданного в `HIT_RATE_THRESH_REG`.
* `Bit [4]` — **`SPI_ADDR_ERR`**: Доступ по адресу вне карты CSR.
* `Bit [5]` — **`I2C_NACK`**: Зафиксирован NACK от выбранного датчика.
* `Bit [6]` — **`I2C_TIMEOUT`**: Истекло время ожидания ответа датчика.
* `Bit [7]` — **`I2C_BUS_ERR`**: Зафиксирована ошибка или зависание I²C-шины.

`FIFO_OVERFLOW` означает, что FIFO достигло полного состояния и передатчик приостановил опрос до появления свободного места. При корректном соблюдении `s_axis_tready` данные не теряются; попытка записи поверх полного FIFO считается отдельной ошибкой, а не штатным условием остановки.
События `FIFO_OVERFLOW`, `I2C_NACK`, `I2C_TIMEOUT` и `I2C_BUS_ERR` фиксируются в `INT_STATUS_REG` до очистки записью единицы в соответствующий бит (W1C). `INT_ENABLE_REG` маскирует источники на выходе `spi_irq`, не отменяя фиксацию статуса.

#### `0x0A` — `CRC_CFG_REG` (CRC Configuration Register — In-Band Sync)

* `Bit [0]` — **`CRC_EN`**: `1` — Включение контроля CRC, `0` — Отключение контроля CRC.
* `Bits [2:1]` — **`CRC_MODE`**:
* `00` — **Idle / Pause Mode:** CRC передается только в моментах простоя входного FIFO.
* `01` — **Block Mode:** CRC передается строго через каждые $M$ переданных 32-битных слов.
* `10` — **Continuous Mode:** CRC добавляется к каждому отдельному кадру.

* `Bits [5:3]` — **`BLOCK_SIZE`**: Длина блока $M$ для Block Mode:
* `000` = 8 слов, `001` = 16 слов, `010` = 32 слова, `011` = 64 слова.

* `Bits [7:6]` — Зарезервировано.

#### `0x0B` — `HIT_RATE_THRESH_REG` (Hit Rate Interrupt Threshold)

* `Bits [7:0]` — **`THRESH_VAL`**: Восьмибитное значение порога эффективности дедупликации ($0 .. 255$, где $255 = 100\%$). Если текущее отношение $CNT\_KEY\_FRAMES / CNT\_TOTAL\_WORDS$ превышает это значение, взводится бит `HIGH_HIT_RATE` в `INT_STATUS_REG`.

## 7. Регистры и карта памяти Приемника (`tdl_rx_top`)

### 7.1. Общие принципы организации CSR

Все регистры блока CSR приемника являются **32-битными** и выравниваются по 4-байтовой границе адреса (смещение каждого следующего регистра `+0x04`). Доступ к регистрам осуществляется по 32-битному потоковому интерфейсу `iolink`.

* **Атомарность:** Чтение и запись 32-битных счетчиков и конфигураций выполняется за один цикл шины `iolink` без использования механизмов Read-Shadowed.
* **Структура памяти:**
* `0x0000 - 0x00FF` — **Общие регистры приемника (Global RX Registers)**.
* `0x0100 + i * 0x0040` — **Канальные регистры ($i$-й канал, Stride = 64 байта)**.

---

### 7.2. Общие регистры приемника (Global Registers, `0x0000 .. 0x00FF`)

| Адрес (Offset) | Название регистра | Доступ | Сброс | Назначение |
| --- | --- | --- | --- | --- |
| `0x0000` | **`RX_GLOBAL_CTRL`** | RW | `0x0000_0000` | Глобальное управление приемником. |
| `0x0004` | **`RX_GLOBAL_STATUS`** | RO | `0x0000_0000` | Сводный статус всех каналов (активность IRQ, ошибки, переполнения). |
| `0x0008` | **`RX_MSI_ADDR`** | RW | `0xFEE0_0000` | Системный адрес назначения для MSI-транзакций `WRITE_REQ`. |
| `0x000C` | **`RX_INT_ENABLE`** | RW | `0x0000_0000` | Глобальная маска разрешений прерываний. |
| `0x0010` | **`RX_INT_STATUS`** | W1C | `0x0000_0000` | Глобальный статус прерываний (Запись '1' сбрасывает бит). |
| `0x0014` | **`RX_ACTIVE_CH_MASK`** | RW | `0x0000_000F` | Маска разрешенных каналов приема (побитовая для $N$ каналов). |
| `0x0018` | **`RX_ARBITER_CTRL`** | RW | `0x0000_0004` | Настройка выходного AXI-арбитра (лимиты burst, алгоритм опроса). |
| `0x001C` | **`CNT_TOTAL_DECODED`** | RO | `0x0000_0000` | 32-битный суммарный счетчик восстановленных слов со всех каналов. |

### 7.3. Канальные регистры приемника (Per-Channel Registers)

Базовый адрес для канала $i$: $\text{BaseAddr}(i) = \mathtt{0x0100} + (i \times \mathtt{0x0040})$.

| Смещение (`Offset`) | Название регистра | Доступ | Сброс | Назначение |
| --- | --- | --- | --- | --- |
| `+0x00` | **`CH_CTRL`** | RW / WO | `0x0000_0001` | Управление каналом (Enable, Soft Reset, Flush FIFO/Dict). |
| `+0x04` | **`CH_STATUS`** | RO | `0x0000_0000` | Статус канала (FIFO, FSM декодера, ошибки, рассинхронизация). |
| `+0x08` | **`CH_INT_ENABLE`** | RW | `0x0000_0000` | Маска разрешений прерываний канала. |
| `+0x0C` | **`CH_INT_STATUS`** | W1C | `0x0000_0000` | Флаги источников прерываний канала (сброс записью '1'). |
| `+0x10` | **`CH_TID_CFG`** | RW | $i$ | Идентификатор источника (`Sensor_ID` / `TID` для `m_axis_out_tid`). |
| `+0x14` | **`CH_MSI_VECTOR`** | RW | $i$ | Payload/Data вектор MSI-прерывания данного канала. |
| `+0x18` | **`CH_ACTIVE_CFG`** | RO | `0x0000_0000` | Текущая конфигурация CRC канала; согласование с передатчиком обеспечивает ЦП. |
| `+0x1C` | **`CH_DICT_STATUS`** | RO | `0x0000_0000` | Состояние заполнения словаря данного канала. |
| `+0x20` | **`CH_TIMEOUT`** | RW | `0x0000_03E8` | 16-битный таймаут ожидания CRC (в тактах `clk`). |
| `+0x24` | **`CNT_CH_CRC_ERRORS`** | RO | `0x0000_0000` | 32-битный счетчик ошибок CRC текущего канала. |
| `+0x28` | **`CNT_CH_DECODED`** | RO | `0x0000_0000` | 32-битный счетчик декодированных слов текущего канала. |
| `+0x2C` | **`CNT_CH_DESYNC`** | RO | `0x0000_0000` | 32-битный счетчик событий рассинхронизации/таймаута. |

---

### 7.4. Детализация битовых полей регистров приемника

#### 7.4.1. Общие регистры

##### `0x0000` — `RX_GLOBAL_CTRL` (Global Control Register)

* `Bit [0]` — **`RX_EN`** (RW): Глобальное включение приемника (`1` — активен, `0` — заблокирован).
* `Bit [1]` — **`GLOBAL_SOFT_RESET`** (WO): Программный сброс FSM декодеров и FIFO всех каналов.
* `Bit [2]` — **`CLR_GLOBAL_COUNTERS`** (WO): Сброс всех 32-битных счетчиков (общих и канальных).
* `Bit [3]` — **`MSI_EN`** (RW): Глобальное разрешение генерации MSI-пакетов в `iolink_tx`.
* `Bits [31:4]` — Reserved.

##### `0x0004` — `RX_GLOBAL_STATUS` (Global Status Register — Read Only)

* `Bit [0]` — **`ANY_IRQ_PENDING`**: Присутствует хотя бы одно активное прерывание на любом из каналов.
* `Bit [1]` — **`ANY_CRC_ERR`**: Зафиксирована ошибка CRC хотя бы на одном канале.
* `Bit [2]` — **`ANY_FIFO_OVF`**: Зафиксировано переполнение FIFO хотя бы на одном канале.
* `Bits [31:3]` — Reserved.

##### `0x0008` — `RX_MSI_ADDR` (Global MSI Target Address)

* `Bits [31:0]` — **`MSI_TARGET_ADDR`** (RW): 32-битный системный адрес (например, контроллера прерываний ЦПУ APIC/GIC), по которому приемник отправляет транзакцию `WRITE_REQ` при вызове прерывания.

##### `0x000C` / `0x0010` — `RX_INT_ENABLE` & `RX_INT_STATUS` (Global Interrupt Mask & Status)

* `Bit [0]` — **`ANY_CHANNEL_IRQ_EN`** (RW): Разрешение системного прерывания от каналов.
* `Bit [1]` — **`ARB_ERROR_EN`** (RW): Разрешение прерывания при ошибке выходного арбитра.
* `Bits [31:2]` — Reserved.

##### `0x0014` — `RX_ACTIVE_CH_MASK` (Active Channels Mask)

* `Bits [N-1:0]` — **`CH_ENABLE_MASK`** (RW): Битовая маска активных каналов приема (`1` — канал участвует в работе и опросе арбитром).

##### `0x0018` — `RX_ARBITER_CTRL` (AXI Arbiter Control)

* `Bits [1:0]` — **`ARB_MODE`** (RW): Алгоритм работы выходного арбитра:
* `00` — **Strict Round-Robin** (Строгий циклический опрос каналов).
* `01` — **Priority Channel 0** (Приоритет Канала 0 для критичных данных).
* `10` — **Weighted Round-Robin** (Учитывает заполнение канальных FIFO).

* `Bits [5:2]` — **`BURST_LIMIT`** (RW): Максимальное количество 32-битных слов (`1 .. 16`), вычитываемое арбитром из одного канала непрерывно перед переключением на следующий.
* `Bits [31:6]` — Reserved.

---

#### 7.4.2. Канальные регистры

##### `+0x00` — `CH_CTRL` (Channel Control Register)

* `Bit [0]` — **`CH_EN`** (RW): Индивидуальное включение данного канала приема.
* `Bit [1]` — **`CH_SOFT_RESET`** (WO): Индивидуальный сброс FSM декодера и FIFO только этого канала.
* `Bit [2]` — **`FLUSH_VAL_FIFO`** (WO Strobe): Принудительный сброс содержимого буфера валидации CRC без выдачи в ЦПУ.
* `Bit [3]` — **`FLUSH_CH_DICT`** (WO Strobe): Принудительная очистка словаря данного канала.
* `Bit [4]` — **`CLR_CH_COUNTERS`** (WO Strobe): Сброс всех счетчиков данного канала (`CNT_CH_*`).
* `Bits [31:5]` — Reserved.

##### `+0x04` — `CH_STATUS` (Channel Status Register — Read Only)

* `Bit [0]` — **`VAL_FIFO_EMPTY`**: Буфер валидации CRC данного канала пуст.
* `Bit [1]` — **`VAL_FIFO_FULL`**: Буфер валидации CRC переполнен (Backpressure error).
* `Bit [2]` — **`RX_FIFO_FULL`**: Выходное канальное FIFO переполнено.
* `Bit [3]` — **`KEY_OUT_OF_RANGE`**: Ошибка рассинхронизации: принят индекс ключа, превышающий `DICT_SIZE`.
* `Bit [4]` — **`CRC_ERROR_STUCK`**: Зафиксирована ошибка CRC в текущем блоке данных.
* `Bit [5]` — **`TIMEOUT_EXPIRED`**: Сработал таймаут ожидания `HEADER_CRC`.
* `Bits [7:6]` — **`CH_FSM_STATE`**: Состояние FSM декодера канала (`00`: IDLE, `01`: PAYLOAD, `10`: WAIT_CRC, `11`: ERROR_FLUSH).
* `Bit [8]` — **`SYNC_ACTIVE`**: Флаг текущей синхронизации канала (`1` — канал синхронизирован).
* `Bits [31:9]` — Reserved.

##### `+0x08` — `CH_INT_ENABLE` (Channel Interrupt Enable)

* `Bit [0]` — **`CRC_ERR_EN`** (RW): Разрешение прерывания при ошибке проверки CRC.
* `Bit [1]` — **`KEY_OOR_EN`** (RW): Разрешение прерывания при выходе индекса ключа за пределы словаря.
* `Bit [2]` — **`TIMEOUT_EN`** (RW): Разрешение прерывания по таймауту ожидания CRC-кадра.
* `Bit [3]` — **`FIFO_OVF_EN`** (RW): Разрешение прерывания при переполнении канального FIFO.
* `Bits [31:4]` — Reserved.

##### `+0x0C` — `CH_INT_STATUS` (Channel Interrupt Status — W1C)

* `Bit [0]` — **`CRC_ERR_STAT`**: Зафиксирована ошибка CRC.
* `Bit [1]` — **`KEY_OOR_STAT`**: Зафиксирована ошибка индекса ключа.
* `Bit [2]` — **`TIMEOUT_STAT`**: Зафиксирован таймаут ожидания CRC.
* `Bit [3]` — **`FIFO_OVF_STAT`**: Зафиксировано переполнение канального FIFO.
* `Bits [31:4]` — Reserved.

##### `+0x10` — `CH_TID_CFG` (Channel TID Configuration)

* `Bits [7:0]` — **`TID_VAL`** (RW): 8-битный идентификатор канала (`m_axis_out_tid`), транслируемый на выходную шину AXI4-Stream.
* `Bits [31:8]` — Reserved.

##### `+0x14` — `CH_MSI_VECTOR` (Channel MSI Data Payload)

* `Bits [31:0]` — **`MSI_DATA_PAYLOAD`** (RW): 32-битный вектор данных, отправляемый в транзакции `WRITE_REQ` по адресу `RX_MSI_ADDR` при вызове прерывания от данного канала.

##### `+0x18` — `CH_ACTIVE_CFG` (Channel Active CRC Configuration — Read Only)

* `Bit [0]` — **`ACTIVE_CRC_EN`**: `1` — Контроль CRC активен в данном канале, `0` — отключен.
* `Bits [2:1]` — **`ACTIVE_CRC_MODE`**: Активный режим расчета CRC (`00`: Idle/Pause, `01`: Block Mode, `10`: Continuous Mode).
* `Bits [5:3]` — **`ACTIVE_BLOCK_SIZE`**: Активный размер блока $M$ (`000`=8, `001`=16, `010`=32, `011`=64 слов).
* `Bits [31:6]` — Reserved.

##### `+0x1C` — `CH_DICT_STATUS` (Channel Dictionary Status — Read Only)

* `Bits [6:0]` — **`OCCUPIED_ENTRIES_SCALED`**: Число занятых ячеек словаря, деленное на 2 ($0 \dots 127$).
* `Bit [7]` — **`DICT_FULL`**: Флаг полного заполнения словаря канала (`1` — все ячейки заняты).
* `Bits [31:8]` — Reserved.

##### `+0x20` — `CH_TIMEOUT` (Channel CRC Timeout Configuration)

* `Bits [15:0]` — **`VAL_TIMEOUT_VAL`** (RW): Таймаут ожидания CRC-кадра в тактах `clk` (по умолчанию `0x03E8` = 1000 тактов). По истечении таймаута буфер валидации сбрасывается, предотвращая зависание канала.
* `Bits [31:16]` — Reserved.

## 8. Алгоритмы дедупликации и политики вытеснения словаря

Управление словарем дедупликации в передатчике (`tdl_tx_top`) выстроено по модульному принципу. Модуль подстраивается под тип и характер трафика (импульсный, с периодическими повторами или локально-стационарный) с помощью переключения поля `ALGO_SEL` в конфигурационном регистре `MODE_REG` (`0x01`).

### 8.1. Tabulation hashing

Для TinyLFU используется `tdl_tab_hash`: четыре независимые функции для слова X из четырёх байтов. `gf2_xor_hash` реализует XOR по битовым маскам и не заменяет tabulation hash.

```text
B3=X[31:24]; B2=X[23:16]; B1=X[15:8]; B0=X[7:0]
h_i(X) = T[i,3][B3] XOR T[i,2][B2] XOR T[i,1][B1] XOR T[i,0][B0]
```

Каждая функция имеет четыре собственные таблицы по 256 констант. Для двух BF-функций ширина таблиц/результатов — 12 бит; для двух CMS-функций — 8 бит. ROM-константы фиксируются в RTL package и используются эталонной моделью. При генерации закрепляются алгоритм, seed, порядок заполнения и версия набора. Текущий набор `TABLE_VERSION=2` с `TABLE_SEED=0x54444C06` закреплён в [tdl_tab_hash_pkg](modules/transmitter/tdl_tab_hash_pkg.md). Runtime изменения таблиц нет. Формула хэша и порядок выдачи результатов описаны в [tdl_tab_hash](modules/transmitter/tdl_tab_hash.md#логика-работы).

Интерфейс — эластичный однорегистровый valid/ready канал. При приёме запроса на фронте T0 четыре результата появляются в выходном регистре после T0; потребитель может принять их на T1. При непрерывном ready принимается один запрос за такт. При stall сохраняются valid и все хэши; новый запрос принимается только при наличии места или одновременной выдаче старого ответа. Физическое отображение ROM в LUTRAM/логику определяется синтезом.

В базовом тракте hash запускается после exact miss через policy. Параллельный запуск с lookup — последующая оптимизация с отдельным ранним интерфейсом. Clock, LFU, SLRU и Bypass hash не используют. Коллизии BF/CMS не создают dictionary hit: exact search сравнивает все 32 бита.

Подробности: [tdl_tab_hash](modules/transmitter/tdl_tab_hash.md).

### 8.2. Общий конвейер принятия решений

Controller фиксирует слово и конфигурацию. Bypass сразу даёт RAW. В остальных режимах выполняется exact lookup, затем вызывается выбранная policy, в том числе на hit для подготовки metadata update.

| Условие | Обработка | Кадр |
| --- | --- | --- |
| Bypass | Без lookup и policy | RAW |
| Exact hit, любой алгоритм | Обновить metadata найденной строки | KEY с ключом exact lookup |
| Miss, Clock/Pure LFU | Свободная строка, при полном словаре — victim policy | SYNC |
| Miss, SLRU | Probationary в пределах квоты, иначе его LRU | SYNC |
| Miss, TinyLFU | BF при включённом фильтре, затем CMS/admission | RAW при отказе, SYNC при допуске |

BF/CMS используются только TinyLFU. Clock/LFU предпочитают свободную строку замещению; TinyLFU — после BF pass или при `BF_EN=0`. SLRU имеет фиксированные квоты и не занимает свободную ёмкость Protected новыми miss.

Storage единолично владеет словами и `valid_bits`. Поиск и политики учитывают только valid-строки. На равных локальных частотах выбирается минимальный ключ; Clock следует кольцевому порядку. Изменения metadata не меняют физический ключ слова.

### 8.3. TinyLFU + CU-CMS + 2×BF (`ALGO_SEL=00`)

#### 8.3.1. Doorkeeper и поколения BF

BF — два вектора по 4096 бит (active/old). Для exact miss при `BF_EN=1` проверка выполняется по состоянию **до** вставки текущего слова:

```text
bf_seen = (active[h_BF1] OR old[h_BF1])
       AND (active[h_BF2] OR old[h_BF2])
```

На commit обоих типов miss, прошедшего и отвергнутого BF, два бита устанавливаются в active. При `bf_seen=0` выдаётся RAW без CMS update; при `bf_seen=1` слово идёт к CMS. False positive может пропустить первое появление к admission: гарантией BF-отказа является отрицательная проверка, а не сам факт первого появления. KEY требует exact hit.

На exact hit BF не обновляется. При `BF_EN=0` проверка, запись и ротация BF отключены, поколения заморожены, каждый exact miss идёт к CMS. Повторное включение использует сохранённую историю без автоматической очистки.

Ротация очищает физическое old-поколение, затем меняет роли: бывший active становится old, очищенный буфер — active. Очистка может быть многоцикловой; до `aging_done` следующий запрос не принимается. Внешний контракт — busy/done, а не обязательная очистка за один такт. Реализация может использовать регистры, последовательную очистку RAM либо метки поколений с корректной обработкой их переполнения.

#### 8.3.2. CMS и оценка после update

CMS содержит две строки по 256 четырёхбитных насыщаемых counters, reset всех ячеек — 0. `h_CMS1` адресует row 0, `h_CMS2` — row 1.

```text
c0 = CMS[0][h_CMS1]; c1 = CMS[1][h_CMS2]
m = min(c0, c1)
sat_inc(c) = (c == 15) ? 15 : c + 1
CU_DISABLE=0: c0_next = (c0 == m) ? sat_inc(c0) : c0
              c1_next = (c1 == m) ? sat_inc(c1) : c1
CU_DISABLE=1: c0_next = sat_inc(c0); c1_next = sat_inc(c1)
f_new = min(c0_next, c1_next)
```

Оба сравнения CU используют один минимум по старым значениям. Оценка после update вычисляется заранее; постоянная память меняется только на commit. CMS сохраняет адреса и будущие counters до подтверждения; при stall повторного инкремента нет.

CMS обновляется на exact miss после BF pass, либо на каждом exact miss при `BF_EN=0`, включая admission-отказ с RAW. Dictionary hit обновляет только local resident counter. CMS оценивает этот поток miss с учётом коллизий, насыщения и aging, а не полное число появлений слова.

#### 8.3.3. Локальные частоты и admission

TinyLFU хранит собственный 4-битный counter на ключ, не разделяемый с Pure LFU. Reset=0, insert/replace=1, exact hit — насыщаемое увеличение до 15. История victim удаляется; значение CMS не переносится в local counter.

После BF pass либо при `BF_EN=0`:

* при свободном месте использовать минимальный свободный ключ без сравнения частот;
* при полном словаре выбрать минимум local counters по valid-строкам, при равенстве — минимальный ключ;
* заменить только при `f_new > f_min`; при равенстве или меньшем значении выдать RAW.

`f_new` отражает прошлые подходящие miss кандидата, `f_min` — обращения к resident-записи после вставки. Это разные истории, принятые для этой реализации. Новый local counter начинается с 1 даже при большом `f_new`.

Если все local counters достигли 15 и aging выключен, ни один кандидат с 4-битной оценкой не удовлетворяет строгому `>`. Замещения прекращаются до уменьшения/переинициализации статистики. Это определённое поведение режима.

#### 8.3.4. Период aging и ротации

Период относится только к активному TinyLFU и считает `policy_commit` каждого non-Bypass слова, включая KEY, RAW и SYNC. AXIS-приём, pop FIFO, циклы ожидания и число CMS updates не являются единицей периода. По умолчанию `N={AGING_PERIOD_HI,AGING_PERIOD_LO}=1024`.

После N-го commit сначала сохраняются обычные изменения слова, затем обслуживается граница периода. До завершения backend блокирует следующий запрос. Новый интервал начинается с нуля. Если N меняется по §6.1.1, первый запрос с новым снимком начинает новый интервал и считается первым на commit. При N=0 период не накапливается.

| Настройки | CMS и local counters | BF |
| --- | --- | --- |
| `N>0`, `AGING_DISABLE=0`, `BF_EN=1` | Каждая ячейка `>>1` | Ротация |
| `N>0`, `AGING_DISABLE=1`, `BF_EN=1` | Без деления | Ротация |
| `N>0`, `AGING_DISABLE=0`, `BF_EN=0` | Каждая ячейка `>>1` | Заморожен |
| `N>0`, `AGING_DISABLE=1`, `BF_EN=0` | Без изменений | Заморожен |
| `N=0` | Периодическое деление отключено | Периодическая ротация отключена |

Сдвиг округляет вниз; нулевые local counters остаются валидными записями. Число тактов обслуживания зависит от памяти. `aging_done` означает завершение всех запрошенных операций: частичное состояние не видно следующему слову. В других алгоритмах и на новых Bypass-словах статистика/период TinyLFU не обновляются; ранее принятое обслуживание завершается штатно.

Подробности: [tdl_tinylfu_policy](modules/transmitter/tdl_tinylfu_policy.md), [tdl_bloom_filter](modules/transmitter/tdl_bloom_filter.md), [tdl_cms](modules/transmitter/tdl_cms.md), [tdl_aging_ctrl](modules/transmitter/tdl_aging_ctrl.md).

### 8.4. Segmental LRU / SLRU (`ALGO_SEL=01`)

SLRU не обращается к hash/BF/CMS. Квоты: `N_prob=SLRU_CFG_REG[7:0]`, `N_prot=DICT_SIZE-N_prob`, `1 <= N_prob < DICT_SIZE`. Default `0x40` при `DICT_SIZE=256` означает 64/192. Это вместимости, а не диапазоны физических ключей. При малом словаре software настраивает допустимый размер до запуска; неверный порог блокирует SLRU через `cfg_valid=0` и выявляется assertion, без скрытого clamp. Новый CSR ошибки не вводится.

Metadata строки: segment tag (0 Probationary, 1 Protected), LRU rank ширины `max(1,$clog2(DICT_SIZE))`. Ранги valid-строк каждого сегмента уникальны: `0…count-1`, 0 — MRU. Reset обнуляет metadata; невалидные строки в порядке не участвуют.

#### 8.4.1. Miss и квоты

При `prob_count < N_prob` используется минимальный свободный физический ключ и вставка в Probationary MRU. При `prob_count == N_prob` заменяется Probationary LRU, даже если в общем словаре есть свободные строки. Свободная квота Protected не заимствуется для miss. Кадр SYNC; metadata и запись слова подтверждаются одним commit.

#### 8.4.2. Hit и переходы

Hit Protected переводит строку в MRU того же сегмента. Hit Probationary переводит её в Protected MRU. Если Protected был полон, его прежний LRU demote-ится в Probationary MRU. Promote освобождает место Probationary, поэтому дополнительный eviction на hit не требуется.

Оба перехода фиксируются атомарно на commit и меняют только segment/rank. Физический ключ и слово остаются прежними; выдаётся KEY исходного `hit_key`.

#### 8.4.3. Точные ранги

```text
Hit внутри сегмента, old_rank=r:
    rank[k] = 0
    для остальных valid-строк сегмента с rank < r: rank += 1
Удаление из сегмента (eviction или переход), old_rank=r:
    для оставшихся valid-строк сегмента с rank > r: rank -= 1
Добавление в MRU:
    ранги всех текущих valid-строк сегмента += 1
    rank[new_key] = 0
```

Replacement логически удаляет victim и добавляет новую запись. Promote/demote состоят из удалений/добавлений с согласованными count; промежуточное состояние не видно следующему запросу. При корректном порядке переполнения/равенств рангов нет. Минимальный ключ — защитный tie-break при повреждённых равных рангах; нарушение также выявляется assertion. Счётчики времени с увеличением всех остальных строк не используются. Aging к SLRU не применяется.

Подробности: [tdl_slru_policy](modules/transmitter/tdl_slru_policy.md).

### 8.5. Clock / second-chance (`ALGO_SEL=10`)

Название Clock / CAR в карте регистров обозначает простой кольцевой second-chance; адаптивные списки CAR не входят в реализацию. Hash/BF/CMS и периодическое aging отключены.

Metadata: `usage_bit[DICT_SIZE]` и `clock_hand[KEY_WIDTH-1:0]`; reset — 0. `next(i)=(i==DICT_SIZE-1)?0:i+1`, включая размеры не степени двойки.

* Hit: на commit usage найденной строки = 1, рука не меняется; KEY.
* Miss при неполном словаре: минимальный свободный ключ, usage = 1, рука не меняется; SYNC.
* Miss при полном словаре: обход с `clock_hand`; единичные usage получают второй шанс и логически очищаются. Первая строка с usage=0 — victim. На commit применить накопленные очистки, затем usage victim=1 и руку `next(victim)`; SYNC.

Очистки хранятся во временной маске/копии, постоянные metadata до commit не меняются. Scan учитывает уже подготовленные очистки, иначе при всех usage=1 обход не завершится. При N единицах требуется N очисток и повторное посещение стартовой строки; допустима оптимизация выбора стартовой строки после полного круга. Выбирать первую очищенную строку сразу, без проверки остальных, нельзя: это меняет second-chance порядок.

Подробности: [tdl_clock_policy](modules/transmitter/tdl_clock_policy.md).

### 8.6. Pure LFU (`ALGO_SEL=11`)

Автономная policy с 4-битными local counters resident-строк: reset=0, insert/replace=1, hit увеличивает counter с насыщением до 15. Учитываются вставка и последующие обращения; новый counter не наследует историю victim.

* Hit: подготовить увеличение `local_cnt[hit_key]`; KEY.
* Miss при неполном словаре: минимальный свободный ключ; SYNC.
* Miss при полном словаре: минимум только по valid-строкам, при равенстве минимальный ключ; SYNC.

Miss всегда допускается. Hash/BF/CMS и автоматическое aging не используются; `AGING_PERIOD/AGING_DISABLE` относятся только к TinyLFU. Насыщение может долго сохранять приоритет старых записей. Дерево минимумов проектируется на 1–2 такта; valid/ready допускает ожидание до готовности результата.

Подробности: [tdl_lfu_policy](modules/transmitter/tdl_lfu_policy.md).

### 8.7. Bypass (`BYPASS_EN=1`)

Слово, захваченное с Bypass, выдаётся как RAW без lookup/policy, dictionary write и `policy_commit`. Оно не изменяет metadata, BF/CMS и период aging. Bypass фиксируется при захвате; его включение не отменяет ранее принятую обычную транзакцию и обслуживание. После завершения прежней работы статистические структуры сохраняются до возобновления обычных запросов.

### 8.8. Ресурсы и аппаратное отображение

Ресурсные оценки не являются результатом синтеза. Частота, LE/LUT и memory blocks измеряются на выбранной FPGA для конкретного RTL. При `DATA_WIDTH=32`, `DICT_SIZE=256` объём полезного состояния TinyLFU:

| Структура | Размер |
| --- | --- |
| Dictionary words | 8192 бит = 1024 байт |
| Valid-маска | 256 бит = 32 байта |
| Local counters | 1024 бит = 128 байт |
| Два поколения BF | 8192 бит = 1024 байта |
| CMS | 2048 бит = 256 байт |
| Изменяемое состояние выше | 2464 байта ≈ 2,406 КиБ |
| 16 byte-ROM hash | `2*4*256*12 + 2*4*256*8 = 40960` бит = 5 КиБ |
| Сумма состояния и ROM выше | 7584 байта ≈ 7,406 КиБ |

FSM, pending updates, FIFO/кадровые буферы и регистры управления не включены. ROM, RAM и регистры учитываются отдельно: 2,4 КиБ без hash-ROM не являются полной памятью TinyLFU. Остальные режимы используют общий dictionary и metadata только соответствующего backend-а. Коэффициент сжатия зависит от потока.

### 8.9. Транзакционный контракт

Controller обрабатывает одно слово: lookup → запрос policy → ответ → descriptor commit. Handshake ответа policy и commit — разные события. Policy остаётся занятой до commit и завершения вызванного им обслуживания; следующий запрос не перезаписывает pending state.

```text
commit = desc_valid && desc_ready
policy_commit = commit && !bypass_q
dict_wr_en = commit && (desc_type == SYNC)
```

Только SYNC меняет физическую строку. KEY обновляет metadata hit; RAW вне Bypass может обновлять BF/CMS. Все эффекты слова выполняются один раз. CMS заранее возвращает post-update оценку и хранит адреса/будущие counters до отдельного commit. Рекомендуются два банка CMS, чтобы подтвердить обе записи одним фронтом. При многоцикловой записи/aging backend остаётся busy до конца: следующему запросу частичное состояние недоступно.

`valid_bits[DICT_SIZE]` выводится из storage через dict_unit в policy без копии владеющего регистра. `dict_full` и минимальный `next_free_key` также берутся из storage; free key недействителен при full. В текущем RTL unit маска ещё внутренняя: это требование доработки.

Контроллер обрабатывает один outstanding запрос без transaction ID. `backend_ready` объединяет готовность поиска и `policy_req_ready` фасада. Фасад вычисляет готовность из состояния выбранной policy и `cfg_valid` по активной конфигурации ещё до выставления `policy_req_valid`. После ответа готовность остаётся снятой до commit и завершения обслуживания. Bypass backend не вызывает; ранее принятая работа завершается независимо от снятия `TX_EN`. Таблица соединений с политиками приведена в [tdl_tx_policy](modules/transmitter/tdl_tx_policy.md#интерфейс-с-backend-политиками).

Запись SYNC до окончания SDR допустима только при порядке SYNC→следующий KEY. Принятый descriptor нельзя отменять или переставлять.

### 8.10. Снимок конфигурации policy

32-битные `policy_cfg/policy_req_cfg` имеют единый формат; controller хранит и передаёт его без декодирования:

| Биты | Поле | Источник |
| --- | --- | --- |
| `[1:0]` | ALGO_SEL | MODE_REG[1:0] |
| `[2]` | CU_DISABLE | MODE_REG[2] |
| `[3]` | AGING_DISABLE | MODE_REG[3] |
| `[4]` | BF_EN | BF_CTRL_REG[0] |
| `[7:5]` | Reserved = 0 | Константа |
| `[15:8]` | N_prob | SLRU_CFG_REG[7:0] |
| `[31:16]` | AGING_PERIOD | {AGING_PERIOD_HI, AGING_PERIOD_LO} |

Это внутренний формат, не последовательность байтов SPI. Общие определения должны появиться в `tdl_tx_pkg`; существующая 32-битная шина controller совместима, но сборка снимка ещё требует реализации. Все четыре двоичных ALGO_SEL определены; X/Z и неправильный SLRU размер выявляются проверками, зарезервированного алгоритма нет.

ALGO_SEL и размеры сегментов задаются до первого захвата после reset и фиксируются до reset. Runtime миграции нет. Остальные параметры изменяются по §6.1.1. `cfg_valid=0` для неверного размера активного SLRU запрещает non-Bypass захват через внешний `backend_ready`; отдельный CSR ошибки не добавляется.

### 8.11. Границы базовой реализации

Правила выше описывают целевую функциональность; отсутствие RTL не означает реализованную поддержку режима. Базовый этап включает RAW/KEY/SYNC, Bypass, четыре policy и автоматическое обслуживание TinyLFU. CRC, I²C, CMD_REG, SOFT_RESET, runtime dictionary flush, BF_RESET и FORCE_ROTATE относятся к последующим этапам. В базовой версии их аппаратные действия отключены, даже если поля есть в RDL.

RX восстанавливает слова по RAW/KEY/SYNC и не повторяет выбор victim. Local counters, ranks, usage, BF/CMS являются TX metadata и не зеркалируются на RX. Будущий протокол reset/смены режима обязан сохранять соответствие используемых ключей и порядок кадров. Восстановление после reset посреди передачи выходит за базовый этап.

Связанные контракты: [policy](modules/transmitter/tdl_tx_policy.md), [controller](modules/transmitter/tdl_tx_controller.md), [dictionary unit](modules/transmitter/tdl_dict_unit.md).

## 9. Система контроля целостности и обработки ошибок

### 9.1. Аппаратный обработчик ошибок (Fast-Path Hardware Error Handler)

Для исключения задержек программного отклика и предотвращения замусоривания словарей рассинхронизированными данными в RTL приемника интегрирован аппаратный FSM обработки ошибок:

```text
       Сбой CRC / Ошибка ключа на шине
                     │
                     ▼
  ┌─────────────────────────────────────┐
  │     ERROR_HANDLER (Fast Path)       │
  ├─────────────────────────────────────┤
  │ 1. Блокировка вывода (tvalid = 0)   │ (Такт N)
  │ 2. Сброс буфера валидации CRC       │ (Такт N)
  │ 3. Запрет записи в словарь RX       │ (Такт N)
  │ 4. Взвод линии прерывания rx_irq    │ (Такт N+1)
  └──────────────────┬──────────────────┘
                     │
                     ▼
        [ Программный уровень ЦПУ ]
         (Логирование и сбор статистики через iolink)

```

* **Изоляция:** При фиксации ошибки CRC или попытке извлечь несуществующий ключ аппаратная логика мгновенно обнуляет валидность кадра, предотвращая попадание мусора в ЦПУ.
* **Защита словаря:** Регистрация изменений в `dictionary[Key]` для сбойного пакета заблокирована.

---

### 9.2. Блочный контроль целостности (Block CRC & Receiver Validation Buffer)

Чтобы исключить 33% оверхед от добавления байта CRC в каждый короткий 2-байтовый кадр `KEY`, в системе реализован режим **Block CRC**:

```text
 Поток байт: [ KEY ] [ KEY ] [ RAW ] ... [ HEADER_CRC (0xD4) ] [ CRC8 ]
             └───────────────────────┘
            Буферизация в Validation FIFO

```

1. **Передатчик (`tdl_tx_top`):** Непрерывно вычисляет полином CRC-8 по всем передаваемым байтам. При возникновении паузы в FIFO или после передачи $M$ слов (задается в `CRC_CFG_REG[5:3]`) передатчик отправляет кадр `HEADER_CRC` (`0xD4`) + `CRC8`.
2. **Приемник (`tdl_rx_top`):** Восстановленные слова накапливаются в промежуточном **Буфере Валидации (Validation FIFO)**. Пропускание пачки слов к ЦПУ происходит единовременно только при успешном совпадении принятого CRC с вычисленным.
