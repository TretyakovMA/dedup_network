## 1. Общие сведения и архитектура системы

Настоящая спецификация описывает архитектуру и интерфейсы макета системы сбора и дедупликации потоковых данных «на лету» (On-the-fly). Система спроектирована для передачи 32-битных значений от нескольких независимых периферийных модулей (передатчиков) к центральному обработчику (приемнику) по узким 8-битным физическим каналам связи.

### 1.1. Границы проектирования (Scope of Design)

#### В рамках данного проекта (In Scope)

* RTL-код передатчика дедуплицированного трафика (`dedup_tx_top`).

* RTL-код приемника, декодеров, буферов валидации и арбитра (`dedup_rx_top`).

* Аппаратный модуль обработки ошибок (`ERROR_HANDLER`) на верхнем уровне.

#### Внешнее оборудование / Отдельные проекты (Out of Scope)

* Физические датчики (АЦП, сенсоры, сканеры).

* Переходной модуль (PHY Bridge): маскирование шумов и сопряжение с физической шиной датчика (SPI, LVDS) вынесены в PHY Bridge. IP-ядро работает с чистым 32-битным потоком AXI4-Stream (`s_data_in`, `s_data_valid`, `s_data_ready`).

### 1.2. Ключевые инженерные решения

* **Экономия выходов (I/O Pins):** Сокращение физического канала между передатчиком и центральной ПЛИС с 32 до 8 бит (экономия 75% пинов).

* **Изоляция каналов (Per-Channel Dictionaries):** Приемник содержит $N$ независимых аппаратных декодеров с собственными словарями, что устраняет узкие места и коллизии.

* **Аппаратная обработка ошибок (Fast-Path Recovery):** Реакция на сбои передачи (ошибки CRC, рассогласование ключей) выполняется аппаратно за 1–2 такта без привлечения ЦПУ, изолируя битый пакет и защищая словари от рассинхронизации.
* **Блочный контроль целостности (Block CRC):** Поддержка гибкой проверки целостности без снижения коэффициента сжатия коротких кадров `KEY`.
* **Бесшовная перенастройка (In-Band Configuration):** Динамическая смена алгоритмов и режимов CRC «на лету» с помощью служебных внутриполосных кадров и теневых регистров.

## 4. Протоколы передачи

### 4.1. Формат кадров от передатчика приемнику

Данные по 8-битной шине передаются пакетами переменной длины. Тип пакета определяется старшим байтом-заголовком (Preamble Header):

```text
1. RAW-кадр (обычный):          [ 0xA1 (Header) ] [ Byte 3 ] [ Byte 2 ] [ Byte 1 ] [ Byte 0 ]
2. KEY-кадр (сжатый):           [ 0xB2 (Header) ] [ Key (8-bit) ]
3. SYNC-кадр (обновление):      [ 0xC3 (Header) ] [ Key (8-bit) ] [ Byte 3 ] [ Byte 2 ] [ Byte 1 ] [ Byte 0 ]
4. CRC-кадр (контроль):         [ 0xD4 (Header) ] [ CRC-8 Payload ]
5. CONFIG-кадр (настройки):     [ 0xE4 (Header) ] [ CFG_BYTE ] [ ~CFG_BYTE ] [ CRC-8 Payload ]

```

| Заголовок | Тип кадра | Длина пакета | Назначение |
| --- | --- | --- | --- |
| `0xA1` | **`HEADER_RAW`** | 5 байт | Передача полных 32-битных данных без изменения словаря. |
| `0xB2` | **`HEADER_KEY`** | 2 байта | Передача 8-битного ключа при совпадении со словарем. |
| `0xC3` | **`HEADER_SYNC`** | 6 байт | Запись/обновление пары «Ключ-Значение» в словаре. |
| `0xD4` | **`HEADER_CRC`** | 2 байта | Проверка накопленной контрольной суммы блока данных (Block/Idle CRC). |
| `0xE4` | **`HEADER_CONFIG`** | 4 байта | Динамическая перенастройка приемника «на лету» с защитой инверсией и CRC. |

При CRC_MODE = 10 (Continuous Mode) в регистре CRC_CFG_REG (см. пункт 6.2) к `HEADER_RAW`, `HEADER_KEY` и `HEADER_SYNC` в конец добавляется байт CRC-8

### 4.2. Протокол управления `iolink` (32-bit Stream)

Межчиповый/внутричиповый интерфейс управления `iolink` представляет собой симметричный потоковый протокол («точка-точка») с управлением потоком `val / data[31:0] / rdy`. Каждое логическое обращение состоит из последовательной передачи 32-битных слов за несколько тактов.

#### **Структура первого сообщения (Header Word, 32 bit)**

Все управляющие флаги и параметры транзакции упакованы в первое 32-битное слово пакета:

```text
 31      28 27          20 19      16 15      12 11       8 7          0
┌──────────┬──────────────┬──────────┬──────────┬──────────┬────────────┐
│  OPCODE  │  REQUEST_ID  │   SIZE   │  STATUS  │    BE    │  RESERVED  │
│ (4 bits) │   (8 bits)   │ (4 bits) │ (4 bits) │ (4 bits) │  (8 bits)  │
└──────────┴──────────────┴──────────┴──────────┴──────────┴────────────┘

```

##### **Описание полей заголовка (`Header[31:0]`)**

* **`OPCODE` (4 бита):** Код операции транзакции.
* **`REQUEST_ID` (8 бит):** Идентификатор транзакции (Tag). Узел-инициатор генерирует ID, узел-исполнитель **обязан скопировать** его в ответный пакет (`READ_RESP` / `WRITE_RESP`).
* **`SIZE` (4 бита):** Размер передаваемого блока данных.
* **`STATUS` (4 бита):** Статус выполнения транзакции (заполняется в ответах `RESP`):
  * `0x0` — **`OKAY`**: Транзакция выполнена успешно.
  * `0x1` — **`DECERR`**: Ошибка декодирования (обращение по несуществующему адресу).
  * `0x2` — **`HW_ERR`**: Фатальный аппаратный сбой (ошибка CRC, таймаут валидации, сбой BRAM).

* **`BE` (Byte Enable) [11:8] (4 бита):** Маска валидных байт в слове данных (`be[3:0]`).
* **`RESERVED` [7:0] (8 бит):** Зарезервировано (заполняется нулями).

---

#### **Поддерживаемые коды операций (`OPCODE`)**

Интерфейсы `iolink` со стороны ЦПУ и Приемника полностью равноправны и используют единый набор команд:

| `OPCODE` | Мнемоника | Данные в пакете | Описание транзакции |
| --- | --- | --- | --- |
| `0x1` | **`READ_REQ`** | Без данных | Запрос на чтение регистра. Последовательность: Header $\rightarrow$ Address. |
| `0x2` | **`WRITE_REQ`** | С данными | Запрос на запись с подтверждением. Последовательность: Header $\rightarrow$ Address $\rightarrow$ Write Data. |
| `0x3` | **`POSTED_WRITE`** | С данными | Запись без ожидания подтверждения (без ответа). Последовательность: Header $\rightarrow$ Address $\rightarrow$ Write Data. |
| `0x8` | **`READ_RESP`** | С данными | Ответ на запрос чтения. Содержит `REQUEST_ID` запроса и `STATUS`. Последовательность: Header $\rightarrow$ Read Data. |
| `0x9` | **`WRITE_RESP`** | Без данных | Подтверждение выполнения записи (`WRITE_REQ`). Содержит `REQUEST_ID` и `STATUS`. Последовательность: Header. |

---

#### **Диаграммы транзакций**

Поток данных передается стробом `val` при наличии готовности `rdy` принимающей стороны.

##### 1. Чтение регистра (ЦПУ $\leftrightarrow$ Приемник)

```text
Инициатор (ЦПУ):
  Такт 1: Header [READ_REQ, ReqID=0x12, SIZE=0, BE=0xF]
  Такт 2: Address [32'h0000_0010] (Регистр CNT_TOTAL_DECODED)

Исполнитель (Приемник):
  Такт 1: Header [READ_RESP, ReqID=0x12, SIZE=1, Status=OKAY]
  Такт 2: Read Data [32'h0000_A12F] (Значение счетчика)

```

##### 2. Запись в регистр CSR (ЦПУ $\leftrightarrow$ Приемник)

```text
Инициатор (ЦПУ):
  Такт 1: Header [WRITE_REQ, ReqID=0x13, SIZE=1, BE=0xF]
  Такт 2: Address [32'h0000_0000] (Регистр RX_GLOBAL_CTRL)
  Такт 3: Write Data [32'h0000_0001] (Данные: RX_EN=1)

Исполнитель (Приемник):
  Такт 1: Header [WRITE_RESP, ReqID=0x13, SIZE=0, Status=OKAY]

```

##### 3. Генерация MSI-прерывания (Приемник $\leftrightarrow$ ЦПУ)

При возникновении ошибки CRC или таймаута Приемник выступает в роли инициатора транзакции записи в системный контроллер прерываний ЦПУ:

```text
Инициатор (Приемник):
  Такт 1: Header [WRITE_REQ, ReqID=0x80, SIZE=1, BE=0xF]
  Такт 2: Address [32'hFEE0_0000] (Системный адрес MSI вектора)
  Такт 3: Interrupt Data [32'h0000_0001] (Payload: CRC Error Ch0)

Исполнитель (ЦПУ):
  Такт 1: Header [WRITE_RESP, ReqID=0x80, SIZE=0, Status=OKAY]

```

### 4.3 Протокол управления `SPI`

Регистры передатчика доступны через встроенный SPI Slave. Каждая транзакция
начинается с установки `spi_cs_n = 0` и состоит из командного байта и байта данных.
Командный байт:

```text
 7           5        1   0
┌────────────┬────────┬───┐
│ RESERVED   │ ADDR   │R/W│
│   [7:6]    │ [5:1]  │   │
└────────────┴────────┴───┘
```

* `ADDR[5:1]` — байтовый адрес регистра из карты раздела 6.2.
* `R/W = 1` — чтение регистра; `R/W = 0` — запись регистра.
* При записи второй байт содержит `DATA[7:0]`. Запрос к регистровому блоку формируется после приема всех восьми бит.
* При чтении второй байт передается ведущим SPI (обычно `0x00`), а ведомый возвращает `DATA[7:0]`.
* `spi_cs_n` должен оставаться в нуле на протяжении обоих байтов. Возврат `spi_cs_n` в единицу завершает транзакцию и сбрасывает состояние SPI-доступа.
* Запись выполняется только после полного приема байта данных. Ошибки доступа к незарезервированному адресу возвращаются как нулевое значение регистра.

## 5. Алгоритм работы и внутренняя логика

### 5.1. Логика Передатчика (`dedup_tx_top`)

#### 1 **Прием данных**

32-битное слово по сигналу `s_data_valid` записывается во **Входное FIFO** (`INPUT_FIFO_DEPTH = 16`). Сигнал `s_data_ready` удерживается в `1`, пока FIFO не заполнится.

#### 2 **Анализ трафика (Encoder FSM)**

Как только FIFO не пусто (`!empty`), FSM извлекает слово и выполняет параллельный поиск в локальном словаре:

* **Hit (Совпадение):** Формируется кадр `HEADER_KEY` (2 байта).
* **Miss (Промах):**
* Если новое слово признано «горячим» (достигло порога повторений), выделяется ключ, формируется кадр `HEADER_SYNC` (6 байт), и пара записывается в локальный словарь.
* Иначе формируется кадр `HEADER_RAW` (5 байт).

#### 3 **Контроль CRC**

Параллельно с передачей байт кадра аппаратный блок CRC8 вычисляет накопительную контрольную сумму. По паузе в FIFO или по достижению порога переданных слов ($M$) FSM внедряет кадр `HEADER_CRC` (`0xD4`).

#### 4 **Смена конфигурации**

При наличии флага `CONFIG_PENDING = 1` FSM передатчика дожидается завершения текущего кадра/блока, внедряет кадр `HEADER_CONFIG` (`0xE4`), выполняет автоматическую очистку словаря (`FLUSH_DICT`) и применяет новые настройки из теневого регистра.

### 5.2. Логика Приемника (`dedup_rx_top`)

#### 1 **Декодирование и Буфер Валидации**

* Приемник содержит $N$ экземпляров модуля `DEDUPLICATOR_RX_CHANNEL`.
* При получении `HEADER_RAW`: Собирает 4 байта и отправляет 32-битное слово в Буфер Валидации.
* При получении `HEADER_SYNC`: Записывает `Value` по адресу `Key` в **свой** словарь и отправляет 32-битное слово в Буфер Валидации.
* При получении `HEADER_KEY`: За **1 такт** извлекает значение из **своего** словаря `dictionary[Key]` и отправляет его в Буфер Валидации.
* Восстановленные слова в **Буфере Валидации (Validation FIFO)** данного канала удерживаются там до тех пор, пока не придет `HEADER_CRC`, если включены соответсвующие настройки.

#### 2 **Проверка CRC**

* При получении кадра `HEADER_CRC` (`0xD4`) приемник сравнивает переданный CRC-8 с аппаратно рассчитанным значением по принятым байтам.
* **CRC совпал:** Данные из буфера валидации переливаются в канальное FIFO и становятся доступны арбитру AXI.
* **CRC НЕ совпал:** Включается аппаратный `ERROR_HANDLER`: данные в буфере валидации маркируются как недействительные и сбрасываются, запись битых ключей в словарь блокируется, взводится линия прерывания `rx_irq`.

#### 3 **Арбитраж**

* Каждое канальное FIFO хранит декодированные 32-битные слова.
* Модуль `AXI_ARBITER` опрашивает канальные FIFO по круговому алгоритму (Round-Robin).
* При наличии данных арбитр забирает слово, выставляет его на выходную шину `m_axis_out_tdata`, а на шину `m_axis_out_tid` выставляет индекс канала (`Sensor_ID`), пропуская данные в ЦПУ.

## 6. Карта регистров управления и состояния Передатчика (`dedup_tx_top`)

Управление регистрами передатчика `dedup_tx_top` осуществляется по интерфейсу
**SPI Slave**. Адресация байтовая, адрес занимает 6 бит.

---

### 6.1. Классификация регистров по способу синхронизации и считывания

Регистры передатчика разделены на три строго изолированные группы:

#### 6.1.1. TX-Local Регистры (Немедленного действия)

Влияют на аппаратные функции локального узла и **применяются мгновенно** после записи
по SPI независимо от состояния передачи трафика и флага `CONFIG_PENDING`:

* **Управление питанием и сбросом (`TX_EN`, `SOFT_RESET`, `CLR_COUNTERS`):** Должны срабатывать немедленно для предотвращения тупиковых ситуаций (Deadlocks) при аварийном сбросе FSM.
* **Настройки алгоритмов допуска:** Выбор порогов, параметров затухания и фильтров Блума.

#### 6.1.2. In-Band Sync Регистры (Теневая запись и внутриполосная синхронизация)

Настройки, изменяющие формат кадров на межчиповой шине, структуру CRC или требующие одновременной перенастройки словарей передатчика и приемника (`CRC_CFG_REG`, `MODE_REG`, а также команда `FLUSH_DICT`).

* **Двухуровневая структура:** Запись по SPI попадает в буферный регистр `STAGED_REG` и выставляет статус `CONFIG_PENDING = 1` в `STATUS_REG`. Рабочий регистр `ACTIVE_REG` продолжит удерживать текущие настройки.
* **Синхронная отправка:** FSM передатчика дожидается завершения передачи текущего кадра или блока данных и формирует внутриполосный кадр `HEADER_CONFIG` (`0xE4`).
* **Структура полезной нагрузки кадра `0xE4` (4 байта):**

1. `0xE4` — Заголовок кадра `HEADER_CONFIG`.
2. `CFG_BYTE` — Конфигурационный байт (содержит упакованные биты `CRC_CFG_REG[5:0]` и `MODE_REG[1:0]`).
3. `~CFG_BYTE` — Побитовая инверсия для аппаратно-быстрой проверки целостности в RX.
4. `CRC-8 Payload` — Контрольная сумма пакета.

* **Атомарный переход:** В момент выдачи кадра `0xE4` передатчик копирует `STAGED_REG` в `ACTIVE_REG`, при необходимости выполняет автоматический сброс словаря (`FLUSH_DICT`) и сбрасывает `CONFIG_PENDING = 0`. Приемник, получив кадр `0xE4` и проверив контрольные суммы, одновременно применяет новую конфигурацию в свой `ACTIVE_REG`.

```text
   ТЕНЕВАЯ ЗАПИСЬ И ВНУТРИПОЛОСНАЯ СИНХРОНИЗАЦИЯ (Write-Staging & In-Band Sync):
    Запись SPI ───────────► [ STAGED_REG ] ──► (Флаг PENDING = 1 в STATUS_REG)
                                 │
                           Ожидание IDLE / Границы кадра
                                 │
                                 ▼
                    Отправка HEADER_CONFIG (0xE4)
                    Payload: [ CFG_BYTE ] [ ~CFG_BYTE ] [ CRC8 ]
                                 │
         ┌───────────────────────┴───────────────────────┐
         ▼                                               ▼
   [ dedup_tx_top ]                             [ DEDUPLICATOR_RX ]
   1. ACTIVE_REG <= STAGED_REG                     1. Проверка: CFG == ~CFG & CRC
   2. Авто-сброс FLUSH_DICT                        2. ACTIVE_REG <= CFG
   3. PENDING <= 0                                 3. Авто-сброс FLUSH_DICT

```

#### 6.1.3. Read-Shadowed Регистры

32-битные счетчики метрик, требующие фиксации чтения (Latch-on-Read) во избежание состояния гонки. При чтении по адресу младшего байта счетчика (например, `0x0C` для `CNT_TOTAL_WORDS`) SPI-доступ фиксирует все 32 бита текущего счетчика в теневой буфер чтения `shadow_rd_reg[31:0]`. Последующие чтения адресов `0x0D`, `0x0E`, `0x0F` выдают байты из зафиксированного `shadow_rd_reg`.

```text
    ТЕНЕВОЕ ЧТЕНИЕ (Read-Shadowing / Latch-on-Read для 32-битных счетчиков):
    Чтение SPI (Byte 0) ──► Фиксация 32-бит счетчика в shadow_rd_reg[31:0]
                            ├─► Возврат Byte 0
    Чтение SPI (Byte 1) ───► Возврат shadow_rd_reg[15:8]   (Без состояния гонки)
    Чтение SPI (Byte 2) ───► Возврат shadow_rd_reg[23:16]
    Чтение SPI (Byte 3) ───► Возврат shadow_rd_reg[31:24]

```

### 6.3. Детализация ключевых регистров Передатчика

#### `0x00` — `CTRL_REG` (Control Register)

* `Bit [0]` — **`TX_EN`**: Включение передатчика (`1` — активен, `0` — заблокирован). Применимо немедленно.
* `Bit [1]` — **`BYPASS_EN`**: Режим сквозной передачи без дедупликации.
* `Bit [2]` — **`SOFT_RESET`**: Программный сброс FSM и FIFO передатчика. Применяется немедленно, сбрасывает текущий пакет и `CONFIG_PENDING`.
* `Bits [7:3]` — Зарезервировано.

#### `0x01` — `MODE_REG` (Algorithm Selection — In-Band Sync)

* `Bits [1:0]` — **`ALGO_SEL`**:
* `00` — **TinyLFU + CU-CMS** (Основной режим: 2×BF + CU-CMS + Затухание).
* `01` — **Segmental LRU (SLRU / 2Q)** (Двухсегментная очередь).
* `10` — **Clock / CAR** (Простой кольцевой алгоритм замещения с флагами).
* `11` — **Pure LFU** (Вытеснение по локальной статистике использования).

* `Bit [2]` — **`CU_DISABLE`**: Отключение Conservative Update (`1` — переключение в стандартный режим CMS).
* `Bit [3]` — **`AGING_DISABLE`**: Отключение автоматического сброса/деления счетчиков на 2.
* `Bits [7:4]` — Зарезервировано.

#### `0x04` — `BF_CTRL_REG` (Bloom Filter Control)

* `Bit [0]` — **`BF_EN`** *(R/W)*: Включение фильтрации одноразовых слов через фильтры Блума (`1` — включено).
* `Bit [1]` — **`FORCE_ROTATE`** *(WO Strobe, Self-Clearing)*: Принудительная ротация фильтров ($BF_{\text{active}} \leftrightarrow BF_{\text{old}}$) и очистка старого фильтра за 1 такт. Запись `1` формирует одиночный строб.
* `Bit [2]` — **`BF_RESET`** *(WO Strobe, Self-Clearing)*: Полная мгновенная очистка обоих фильтров Блума.
* `Bits [7:3]` — Зарезервировано.

#### `0x07` — `CMD_REG` (Command Register — WO Strobes, Auto-Clearing)

* `Bit [0]` — **`FLUSH_DICT_CMD`**: Запрос принудительной очистки словаря. Передатчик защелкивает `FLUSH_BUSY` = 1, дожидается паузы, отправляет служебный кадр 0xE4, обнуляет словари и сбрасывает `FLUSH_BUSY` = 0.

* `Bit [1]` — **`CLR_COUNTERS_CMD`**: Однотактный импульс сброса всех счетчиков производительности.

* `Bits [7:2]` — Зарезервировано.

#### `0x08` — `STATUS_REG` (Status Register — Read Only)

* `Bit [0]` — **`IN_FIFO_EMPTY`**: Входное FIFO пусто.
* `Bit [1]` — **`IN_FIFO_FULL`**: Входное FIFO переполнено.
* `Bit [2]` — **`CONFIG_PENDING`**: Флаг наличия примененных ЦПУ, но еще не отправленных в шину настроек из `STAGED_REG`.
* `Bit [3]` — **`FLUSH_BUSY`**: `1` — идет процесс сброса словарей и отправки `0xE4` (программное обеспечение должно ожидать `0`).
* `Bit [4]` — **`RESET_BUSY`**: `1` — идет процесс аппаратного сброса/инициализации BRAM.
* `Bits [7:5]` — **`FSM_STATE`**: Текущий код состояния кодера.

#### `0x09` / `0x0A` — `INT_ENABLE_REG` & `INT_STATUS_REG` (Interrupt Control)

* `Bit [0]` — **`FIFO_OVERFLOW`**: Прерывание по переполнению входного FIFO.
* `Bit [1]` — **`FIFO_UNDERFLOW`**: Прерывание по попытке чтения из пустого FIFO.
* `Bit [2]` — **`AGING_EVENT`**: Прерывание при наступлении очередного цикла ротации Блума и затухания счетчиков.
* `Bit [3]` — **`HIGH_HIT_RATE`**: Прерывание при превышении порога коэффициента дедупликации, заданного в `HIT_RATE_THRESH_REG`.
* `Bits [7:4]` — Зарезервировано.

#### `0x0B` — `CRC_CFG_REG` (CRC Configuration Register — In-Band Sync)

* `Bit [0]` — **`CRC_EN`**: `1` — Включение контроля CRC, `0` — Отключение контроля CRC.
* `Bits [2:1]` — **`CRC_MODE`**:
* `00` — **Idle / Pause Mode:** CRC передается только в моментах простоя входного FIFO.
* `01` — **Block Mode:** CRC передается строго через каждые $M$ переданных 32-битных слов.
* `10` — **Continuous Mode:** CRC добавляется к каждому отдельному кадру.

* `Bits [5:3]` — **`BLOCK_SIZE`**: Длина блока $M$ для Block Mode:
* `000` = 8 слов, `001` = 16 слов, `010` = 32 слова, `011` = 64 слова.

* `Bits [7:6]` — Зарезервировано.

#### `0x0C` — `HIT_RATE_THRESH_REG` (Hit Rate Interrupt Threshold)

* `Bits [7:0]` — **`THRESH_VAL`**: Восьмибитное значение порога эффективности дедупликации ($0 .. 255$, где $255 = 100\%$). Если текущее отношение $CNT\_KEY\_FRAMES / CNT\_TOTAL\_WORDS$ превышает это значение, взводится бит `HIGH_HIT_RATE` в `INT_STATUS_REG`.

## 7. Регистры и карта памяти Приемника (`dedup_rx_top`)

### 7.1. Общие принципы организации CSR

Все регистры блока CSR приемника являются **32-битными** и выравниваются по 4-байтовой границе адреса (смещение каждого следующего регистра `+0x04`). Доступ к регистрам осуществляется по 32-битному потоковому интерфейсу `iolink`.

* **Атомарность:** Чтение и запись 32-битных счетчиков и конфигураций выполняется за один цикл шины `iolink` без использования механизмов Read-Shadowed.
* **Структура памяти:**
* `0x0000 - 0x00FF` — **Общие регистры приемника (Global RX Registers)**.
* `0x0100 + i * 0x0040` — **Канальные регистры ($i$-й канал, Stride = 64 байта)**.

---

### 7.2. Общие регистры приемника (Global Registers, `0x0000 .. 0x00FF`)

| Адрес (Offset) | Название регистра | Доступ | Сброс | Назначение |
| --- | --- | --- | --- | --- |
| `0x0000` | **`RX_GLOBAL_CTRL`** | RW | `0x0000_0000` | Глобальное управление приемником. |
| `0x0004` | **`RX_GLOBAL_STATUS`** | RO | `0x0000_0000` | Сводный статус всех каналов (активность IRQ, ошибки, переполнения). |
| `0x0008` | **`RX_MSI_ADDR`** | RW | `0xFEE0_0000` | Системный адрес назначения для MSI-транзакций `WRITE_REQ`. |
| `0x000C` | **`RX_INT_ENABLE`** | RW | `0x0000_0000` | Глобальная маска разрешений прерываний. |
| `0x0010` | **`RX_INT_STATUS`** | W1C | `0x0000_0000` | Глобальный статус прерываний (Запись '1' сбрасывает бит). |
| `0x0014` | **`RX_ACTIVE_CH_MASK`** | RW | `0x0000_000F` | Маска разрешенных каналов приема (побитовая для $N$ каналов). |
| `0x0018` | **`RX_ARBITER_CTRL`** | RW | `0x0000_0004` | Настройка выходного AXI-арбитра (лимиты burst, алгоритм опроса). |

| Смещение (`Offset`) | Название регистра | Доступ | Сброс | Назначение |

| `+0x18` | **`CH_ACTIVE_CFG`** | RO | `0x0000_0000` | Активная конфигурация CRC (получена из кадра `0xE4`). |

| `+0x20` | **`CH_TIMEOUT`** | RW | `0x0000_03E8` | 16-битный таймаут ожидания CRC (в тактах `clk`). |
| `+0x24` | **`CNT_CH_CRC_ERRORS`** | RO | `0x0000_0000` | 32-битный счетчик ошибок CRC текущего канала. |
| `+0x28` | **`CNT_CH_DECODED`** | RO | `0x0000_0000` | 32-битный счетчик декодированных слов текущего канала. |
| `+0x2C` | **`CNT_CH_DESYNC`** | RO | `0x0000_0000` | 32-битный счетчик событий рассинхронизации/таймаута. |

### 7.4. Детализация битовых полей регистров приемника

#### 7.4.1. Общие регистры

##### `0x0000` — `RX_GLOBAL_CTRL` (Global Control Register)

* `Bit [0]` — **`RX_EN`** (RW): Глобальное включение приемника (`1` — активен, `0` — заблокирован).
* `Bit [1]` — **`GLOBAL_SOFT_RESET`** (WO): Программный сброс FSM декодеров и FIFO всех каналов.
* `Bit [2]` — **`CLR_GLOBAL_COUNTERS`** (WO): Сброс всех 32-битных счетчиков (общих и канальных).
* `Bit [3]` — **`MSI_EN`** (RW): Глобальное разрешение генерации MSI-пакетов в `iolink_tx`.
* `Bits [31:4]` — Reserved.

##### `0x0004` — `RX_GLOBAL_STATUS` (Global Status Register — Read Only)

* `Bit [0]` — **`ANY_IRQ_PENDING`**: Присутствует хотя бы одно активное прерывание на любом из каналов.
* `Bit [1]` — **`ANY_CRC_ERR`**: Зафиксирована ошибка CRC хотя бы на одном канале.
* `Bit [2]` — **`ANY_FIFO_OVF`**: Зафиксировано переполнение FIFO хотя бы на одном канале.
* `Bits [31:3]` — Reserved.

##### `0x0008` — `RX_MSI_ADDR` (Global MSI Target Address)

* `Bits [31:0]` — **`MSI_TARGET_ADDR`** (RW): 32-битный системный адрес (например, контроллера прерываний ЦПУ APIC/GIC), по которому приемник отправляет транзакцию `WRITE_REQ` при вызове прерывания.

##### `0x000C` / `0x0010` — `RX_INT_ENABLE` & `RX_INT_STATUS` (Global Interrupt Mask & Status)

* `Bit [0]` — **`ANY_CHANNEL_IRQ_EN`** (RW): Разрешение системного прерывания от каналов.
* `Bit [1]` — **`ARB_ERROR_EN`** (RW): Разрешение прерывания при ошибке выходного арбитра.
* `Bits [31:2]` — Reserved.

##### `0x0014` — `RX_ACTIVE_CH_MASK` (Active Channels Mask)

* `Bits [N-1:0]` — **`CH_ENABLE_MASK`** (RW): Битовая маска активных каналов приема (`1` — канал участвует в работе и опросе арбитром).

##### `0x0018` — `RX_ARBITER_CTRL` (AXI Arbiter Control)

* `Bits [1:0]` — **`ARB_MODE`** (RW): Алгоритм работы выходного арбитра:
* `00` — **Strict Round-Robin** (Строгий циклический опрос каналов).
* `01` — **Priority Channel 0** (Приоритет Канала 0 для критичных данных).
* `10` — **Weighted Round-Robin** (Учитывает заполнение канальных FIFO).

* `Bits [5:2]` — **`BURST_LIMIT`** (RW): Максимальное количество 32-битных слов (`1 .. 16`), вычитываемое арбитром из одного канала непрерывно перед переключением на следующий.
* `Bits [31:6]` — Reserved.

---

#### 7.4.2. Канальные регистры

##### `+0x00` — `CH_CTRL` (Channel Control Register)

* `Bit [0]` — **`CH_EN`** (RW): Индивидуальное включение данного канала приема.
* `Bit [1]` — **`CH_SOFT_RESET`** (WO): Индивидуальный сброс FSM декодера и FIFO только этого канала.
* `Bit [2]` — **`FLUSH_VAL_FIFO`** (WO Strobe): Принудительный сброс содержимого буфера валидации CRC без выдачи в ЦПУ.
* `Bit [3]` — **`FLUSH_CH_DICT`** (WO Strobe): Принудительная очистка словаря данного канала.
* `Bit [4]` — **`CLR_CH_COUNTERS`** (WO Strobe): Сброс всех счетчиков данного канала (`CNT_CH_*`).
* `Bit [5]` — **`INBAND_SYNC_EN`** (RW): Разрешение автоматического приема кадра конфигурации `0xE4`.
* `Bits [31:6]` — Reserved.

##### `+0x04` — `CH_STATUS` (Channel Status Register — Read Only)

* `Bit [0]` — **`VAL_FIFO_EMPTY`**: Буфер валидации CRC данного канала пуст.
* `Bit [1]` — **`VAL_FIFO_FULL`**: Буфер валидации CRC переполнен (Backpressure error).
* `Bit [2]` — **`RX_FIFO_FULL`**: Выходное канальное FIFO переполнено.
* `Bit [3]` — **`KEY_OUT_OF_RANGE`**: Ошибка рассинхронизации: принят индекс ключа, превышающий `DICT_SIZE`.
* `Bit [4]` — **`CRC_ERROR_STUCK`**: Зафиксирована ошибка CRC в текущем блоке данных.
* `Bit [5]` — **`TIMEOUT_EXPIRED`**: Сработал таймаут ожидания `HEADER_CRC`.
* `Bits [7:6]` — **`CH_FSM_STATE`**: Состояние FSM декодера канала (`00`: IDLE, `01`: PAYLOAD, `10`: WAIT_CRC, `11`: ERROR_FLUSH).
* `Bit [8]` — **`SYNC_ACTIVE`**: Флаг текущей синхронизации канала (`1` — канал синхронизирован).
* `Bits [31:9]` — Reserved.

##### `+0x08` — `CH_INT_ENABLE` (Channel Interrupt Enable)

* `Bit [0]` — **`CRC_ERR_EN`** (RW): Разрешение прерывания при ошибке проверки CRC.
* `Bit [1]` — **`KEY_OOR_EN`** (RW): Разрешение прерывания при выходе индекса ключа за пределы словаря.
* `Bit [2]` — **`TIMEOUT_EN`** (RW): Разрешение прерывания по таймауту ожидания CRC-кадра.
* `Bit [3]` — **`FIFO_OVF_EN`** (RW): Разрешение прерывания при переполнении канального FIFO.
* `Bit [4]` — **`CFG_UPDATED_EN`** (RW): Разрешение прерывания при смене конфигурации по кадру `0xE4`.
* `Bits [31:5]` — Reserved.

##### `+0x0C` — `CH_INT_STATUS` (Channel Interrupt Status — W1C)

* `Bit [0]` — **`CRC_ERR_STAT`**: Зафиксирована ошибка CRC.
* `Bit [1]` — **`KEY_OOR_STAT`**: Зафиксирована ошибка индекса ключа.
* `Bit [2]` — **`TIMEOUT_STAT`**: Зафиксирован таймаут ожидания CRC.
* `Bit [3]` — **`FIFO_OVF_STAT`**: Зафиксировано переполнение канального FIFO.
* `Bit [4]` — **`CFG_UPDATED_STAT`**: Принята и применена новая конфигурация `0xE4`.
* `Bits [31:5]` — Reserved.

##### `+0x10` — `CH_TID_CFG` (Channel TID Configuration)

* `Bits [7:0]` — **`TID_VAL`** (RW): 8-битный идентификатор канала (`m_axis_out_tid`), транслируемый на выходную шину AXI4-Stream.
* `Bits [31:8]` — Reserved.

##### `+0x14` — `CH_MSI_VECTOR` (Channel MSI Data Payload)

* `Bits [31:0]` — **`MSI_DATA_PAYLOAD`** (RW): 32-битный вектор данных, отправляемый в транзакции `WRITE_REQ` по адресу `RX_MSI_ADDR` при вызове прерывания от данного канала.

##### `+0x18` — `CH_ACTIVE_CFG` (Channel Active CRC Configuration — Read Only)

* `Bit [0]` — **`ACTIVE_CRC_EN`**: `1` — Контроль CRC активен в данном канале, `0` — отключен.
* `Bits [2:1]` — **`ACTIVE_CRC_MODE`**: Активный режим расчета CRC (`00`: Idle/Pause, `01`: Block Mode, `10`: Continuous Mode).
* `Bits [5:3]` — **`ACTIVE_BLOCK_SIZE`**: Активный размер блока $M$ (`000`=8, `001`=16, `010`=32, `011`=64 слов).
* `Bits [31:6]` — Reserved.

##### `+0x1C` — `CH_DICT_STATUS` (Channel Dictionary Status — Read Only)

* `Bits [6:0]` — **`OCCUPIED_ENTRIES_SCALED`**: Число занятых ячеек словаря, деленное на 2 ($0 \dots 127$).
* `Bit [7]` — **`DICT_FULL`**: Флаг полного заполнения словаря канала (`1` — все ячейки заняты).
* `Bits [31:8]` — Reserved.

##### `+0x20` — `CH_TIMEOUT` (Channel CRC Timeout Configuration)

* `Bits [15:0]` — **`VAL_TIMEOUT_VAL`** (RW): Таймаут ожидания CRC-кадра в тактах `clk` (по умолчанию `0x03E8` = 1000 тактов). По истечении таймаута буфер валидации сбрасывается, предотвращая зависание канала.
* `Bits [31:16]` — Reserved.

## 8. Алгоритмы дедупликации и политики вытеснения словаря

Управление словарем дедупликации в передатчике (`dedup_tx_top`) выстроено по модульному принципу. Модуль подстраивается под тип и характер трафика (импульсный, с периодическими повторами или локально-стационарный) с помощью переключения поля `ALGO_SEL` в конфигурационном регистре `MODE_REG` (`0x01`).

### 8.1. Модуль вычисления хэш-функций

Вычисление адресов для фильтров Блума ($BF$) и таблицы CU-CMS выполняется аппаратно за **1 такт** с использованием алгоритма **Tabulation Hashing** (Табулированное хэширование).
Входное 32-битное слово расщепляется на 4 байта: $X = [B_3, B_2, B_1, B_0]$. Вычисление любой $i$-й хэш-функции осуществляется по формуле:

$$h_i(X) = T_{i,3}[B_3] \oplus T_{i,2}[B_2] \oplus T_{i,1}[B_1] \oplus T_{i,0}[B_0]$$

Где $T_{i,0..3}$ — таблицы случайных констант размером $256 \times W$, синтезируемые в Distributed RAM (LUTRAM).

* **Хэш-функции Фильтров Блума ($h_{BF1}, h_{BF2}$):** Разрядность $W = 12$ бит ($0 \dots 4095$).
* **Хэш-функции Таблицы CU-CMS ($h_{CMS1}, h_{CMS2}$):** Разрядность $W = 8$ бит ($0 \dots 255$).

---

### 8.2. Общий конвейер принятия решений (Admission & Eviction Pipeline)

Перед обработкой выбранным алгоритмом каждое поступающее от датчика 32-битное слово $X$ проходит единый входной конвейер кодера:

```text
               Входное 32-битное слово (X)
                           │
                           ▼
             ┌───────────────────────────┐
             │ Поиск в словаре (Hit/Miss)│
             └─────────────┬─────────────┘
                           │
               Совпадение найдено (Hit)?
               /                       \
         ДА (Hit)                     НЕТ (Miss)
           /                             \
          ▼                               ▼
 1. Обновление статистики      1. Проверка через фильтр Блума (Doorkeeper)
    словари (LRU/Freq)         2. Если прошел (≥2-й раз) ──► Оценка алгоритмом admission
 2. Формирование KEY-кадра        - TinyLFU / SLRU / Clock / Pure LFU
    (2 байта)                  3. Выбор: 
                                  - SYNC-кадр (6 байт) + замена ячейки f_min
                                  - RAW-кадр  (5 байт) без изменения словаря

```

---

### 8.3. Основной режим: TinyLFU + CU-CMS + 2×BF (`ALGO_SEL = 00`)

Основной и наиболее эффективный режим работы IP-ядра, обеспечивающий максимальный коэффициент сжатия трафика при сложных паттернах данных.

```text
                    Входное слово (X) [Miss в словаре]
                                   │
                                   ▼
                   ┌──────────────────────────────┐
                   │ Двухбуферный Фильтр Блума    │
                   │  (BF_active  |  BF_old)      │
                   └───────────────┬──────────────┘
                                   │
                           Hit в фильтрах BF?
                           /                \
                     ДА (≥ 2-й раз)        НЕТ (1-й раз / One-Hit)
                         /                    \
                        ▼                      ▼
           ┌────────────────────────┐   Запись X в BF_active.
           │ Инкремент CU-CMS (2×256)│   Словарь не меняется.
           └────────────┬───────────┘   Отправка RAW-кадра (5B)
                        │
                        ▼
      Оценка частоты слова: f_new = min(CMS)
                        │
                        ▼
            Сравнение: f_new > f_min?
            /                       \
      ДА (Горячее)              НЕТ (Холодное)
          /                           \
         ▼                             ▼
 Замена ячейки f_min в словаре.   Отправка RAW-кадра (5B).
 Запись пары [Key, X].            Словарь не меняется.
 Отправка SYNC-кадра (6B).

```

#### 8.3.1. Вращающийся фильтр Блума (Doorkeeper / Вратник)

Служит для отсечения «одноразовых» слов (One-Hit Wonders), предотвращая загрязнение таблицы статистики CMS и словаря.

* **Структура:** Два параллельных вектора памяти $BF_1$ и $BF_2$ размером по 4096 бит ($2^{12}$ бит).
* **Хэширование:** Для каждого слова $X$ параллельно вычисляются две 12-битные хэш-функции $h_{BF1}(X)$ и $h_{BF2}(X)$ ($k=2$).

##### Логика работы

* Элемент признается присутствующим в фильтре, если выполнены условия:

$$(BF_{\text{active}}[h_{BF1}(X)] \lor BF_{\text{old}}[h_{BF1}(X)]) \land (BF_{\text{active}}[h_{BF2}(X)] \lor BF_{\text{old}}[h_{BF2}(X)]) = 1$$

* Новое слово **всегда** записывается в текущий активный фильтр по обоим индексам:

$$BF_{\text{active}}[h_{BF1}(X)] \leftarrow 1, \quad BF_{\text{active}}[h_{BF2}(X)] \leftarrow 1$$

* **Ротация:** Каждые $N$ обработанных слов (по умолчанию $N = 1024$):
* $BF_{\text{old}}$ сбрасывается в `0` за 1 такт.
* Фильтры меняются ролями ($BF_{\text{active}} \leftrightarrow BF_{\text{old}}$).

#### 8.3.2. Оценка частоты через CU-CMS (Conservative Update Count-Min Sketch)

Для слов, прошедших фильтр Блума, выполняется подсчет накопительной частоты.

* **Структура:** Таблица из 2 строк ($d = 2$) по 256 колонок ($w = 256$). Каждая ячейка — 4-битный счетчик с насыщением ($0 .. 15$).
* **Хэширование:** Используются две независимые 8-битные хэш-функции $h_{CMS1}(X)$ и $h_{CMS2}(X)$, адресующие ячейки в 0-й и 1-й строках таблицы соответственно.
* **Алгоритм Conservative Update:** При инкременте частоты слова $X$ увеличиваются на $+1$ **только те счетчики**, значение которых равно минимальному из двух прочитанных по адресам $h_{CMS1}(X)$ (в строке 0) и $h_{CMS2}(X)$ (в строке 1). Это снижает завышение частоты из-за коллизий более чем в 3 раза.

#### 8.3.3. Механизм затухания (Aging)

Для адаптации к смене характера данных одновременно с ротацией фильтров Блума (каждые $N = 1024$ слов) происходит автоматическое затухание статистики:

* Все 4-битные счетчики таблицы CMS и счетчики статистики словаря делятся на 2 (побитовый сдвиг вправо `>> 1`).

#### 8.3.4. Политика вытеснения (Admission decision)

* Дерево компараторов словаря находит ячейку с минимальной локальной частотой $f_{\text{min}}$.
* Новое слово $X$ с оцененной частотой $f_{\text{new}}$ записывается в словарь на место $f_{\text{min}}$ **только если $f_{\text{new}} > f_{\text{min}}$** (формируется `SYNC`-кадр). В противном случае передается `RAW`-кадр.

### 8.4. Режим Segmental LRU / 2Q (`ALGO_SEL = 01`)

Режим **Segmental LRU (SLRU)** является **полностью автономным алгоритмом** вытеснения словаря и работает отдельно от таблицы CU-CMS и фильтров Блума (блока Doorkeeper). В этом режиме вычисление хэш-функций и обращение к CMS-памяти отключаются, что существенно снижает потребление динамической мощности ПЛИС.

Алгоритм разделяет 256 ячеек словаря дедупликации на два независимых логических сегмента: **Probationary** (Пробационный) и **Protected** (Защищенный). Разделение регулируется регистром `SLRU_CFG_REG` (`0x05`).

```text
                        Входное слово (X)
                                │
               ┌────────────────┴────────────────┐
               │  Параллельный поиск в словаре   │
               └────────────────┬────────────────┘
                                │
                      Результат поиска?
                      /               \
                Hit (Совпадение)     Miss (Промах)
                /                       \
               ▼                         ▼
   Где найдено слово X?             1. Запись X в Probationary
   ├── В Protected:                 2. Если Probationary переполнен:
   │   └─ Обновление LRU (MRU)         вытеснение самого старого (LRU)
   └── В Probationary:              3. Отправка SYNC-кадра (6 байт)
       ├─ Повышение (Promote) в Protected
       ├─ Если Protected переполнен:
       │  понижение (Demote) LRU обратно в Probationary
       └─ Отправка KEY-кадра (2 байта)

```

#### 8.4.1. Структура и разделение словаря

Словарь из 256 ячеек разделен на две логические группы с динамическим или статическим распределением:

1. **Пробационный сегмент ($N_{\text{prob}}$ ячеек):** Служит буфером допуска. Новые слова, отсутствующие в словаре, сразу помещаются сюда.
2. **Защищенный сегмент ($N_{\text{prot}}$ ячеек):** Хранит слова, показавшие повторные совпадения. Элементы из этого сегмента не могут быть напрямую вытеснены новыми входящими словами.

Длина каждого сегмента определяется выражением: $N_{\text{prob}} + N_{\text{prot}} = \text{DICT\_SIZE} = 256$.

#### 8.4.2. Логика переходов и правила обработки кадров

##### 1 **Обработка промаха (Miss):**

* Входящее слово $X$ отсутствует в обоих сегментах.
* $X$ записывается в пробационный сегмент в позицию Most Recently Used (MRU).
* **Политика вытеснения:** Если пробационный сегмент заполнен, из него вытесняется (удаляется из словаря) элемент в позиции Least Recently Used (LRU).
* **Передача по шине:** Формируется кадр записи **`HEADER_SYNC` (6 байт)**.

##### 2 **Обработка совпадения в Пробационном сегменте (Hit in Probationary):**

* Слово $X$ найдено в пробационном сегменте (подтвердило свою полезность).
* **Повышение (Promote):** Слово $X$ извлекается из пробационного сегмента и переносится в защищенный сегмент на место MRU.
* **Понижение (Demote):** Если защищенный сегмент в этот момент заполнен, его самый старый элемент (LRU из Protected) вытесняется обратно в пробационный сегмент на место MRU.
* **Передача по шине:** Формируется сжатый кадр **`HEADER_KEY` (2 байта)**.

##### 3 **Обработка совпадения в Защищенном сегменте (Hit in Protected):**

* Слово $X$ найдено в защищенном сегменте.
* Слово $X$ обновляет свой статус, перемещаясь на позицию MRU внутри защищенного сегмента.
* **Передача по шине:** Формируется сжатый кадр **`HEADER_KEY` (2 байта)**.

#### 8.4.3. Аппаратная реализация учета возраста (Hardware LRU Tracking)

Для отслеживания порядка использования слов в RTL без использования ресурсов BRAM под сложную связную структуру данных применяется массив 8-битных счетчиков возраста (`age_counters[0:256-1]`) и 1-битный вектор сегмента (`segment_vector[0:256-1]`, где `0` — Probationary, `1` — Protected):

* **При обращении/добавлении (Hit / Insert):** Счетчик вызванной ячейки сбрасывается в `0` (позиция MRU). Счетчики всех остальных ячеек того же сегмента инкрементируются на $+1$.
* **Поиск кандидата на вытеснение (LRU Lookup):** Параллельное дерево компараторов ищет ячейку с максимальным значением счетчика возраста `age_counters` отдельно внутри подмножества `segment_vector == 0` (для пробационного) и `segment_vector == 1` (для защищенного).

### 8.5. Кольцевой режим Clock / CAR (`ALGO_SEL = 10`)

В этом режиме таблица CMS, логика подсчета суммарных частот и фильтры Блума полностью отключаются (bypassed).

Режим разработан специально для максимального упрощения RTL-логики и достижения наивысшей тактовой частоты ($f_{\text{max}}$) на бюджетных ПЛИС. Алгоритм не требует построения сложных деревьев поиска минимума/максимума и заменяет сортировку элементов сканированием кольцевого указателя.

#### 8.5.1. Метаданные и структура

* За каждой из 256 ячеек словаря закреплен только **1 бит использования** (`usage_bit`).
* Логика содержит единственный 8-битный кольцевой указатель (`clock_hand`), инициализируемый в `0x00`.

#### 8.5.2. Логика работы автомата состояний (FSM)

##### 1 **При совпадении (Hit):**

* Вызываемая ячейка словаря сбрасывает свой `usage_bit = 1`.
* Выдается сжатый кадр **`HEADER_KEY` (2 байта)**.
* Кольцевой указатель `clock_hand` остаётся на месте.

##### 2 **При промахе (Miss):**

* Включается сканирование словаря указателем `clock_hand`:
* Если ячейка, на которую указывает `clock_hand`, имеет `usage_bit == 1`, бит сбрасывается в `0`, а указатель инкрементируется: `clock_hand = clock_hand + 1`.
* Первая же ячейка с `usage_bit == 0` признается кандидатом на замещение.

* Новое 32-битное слово $X$ записывается в найденную ячейку.
* Для этой ячейки устанавливается `usage_bit = 1`.
* Указатель сдвигается на следующий элемент: `clock_hand = clock_hand + 1`.
* Выдается кадр записи **`HEADER_SYNC` (6 байт)**.

---

### 8.6. Вспомогательный режим Pure LFU (`ALGO_SEL = 11`)

Режим **Pure LFU** — автономный алгоритм локального вытеснения. Статистика собирается напрямую внутри словаря только для находящихся в нем 256 элементов.

#### 8.6.1. Метаданные и структура

* Для каждой из 256 ячеек словаря выделяется **индивидуальный локальный 4-битный счетчик Hit-ов** (`local_cnt[0:255]`) со значением от `0` до `15`.

#### 8.6.2. Логика работы автомата состояний (FSM)

##### **При совпадении (Hit):**

* Счетчик совпадений найденной ячейки инкрементируется: `local_cnt[key] = local_cnt[key] + 1` (с насыщением на уровне 15).
* Выдается сжатый кадр **`HEADER_KEY` (2 байта)**.

##### **При промахе (Miss):**

* Параллельное дерево компараторов за 1–2 такта находит ячейку $K_{\text{min}}$ с наименьшим значением локального счетчика `min(local_cnt)`.
* Новое слово $X$ перезаписывает ячейку $K_{\text{min}}$.
* Локальный счетчик новой ячейки инициализируется единицей: `local_cnt[K_min] = 1`.
* Выдается кадр записи **`HEADER_SYNC` (6 байт)**.

#### Главное отличие от TinyLFU+CMS (Режим `00` vs Режим `11`)

* **Pure LFU (`11`):** Уязвим для «одноразовых» всплесков трафика (One-Hit Wonders). Новое редкое слово может вытеснить из словаря полезное слово с низким счетчиком, так как у алгоритма нет предварительного фильтра допуска (Doorkeeper).
* **TinyLFU+CMS (`00`):** Использует фильтры Блума и внешнюю таблицу CU-CMS для проверки слова *до того*, как разрешить ему обновить словарь.

---

### 8.7. Режим сквозной передачи Bypass (`BYPASS_EN = 1`)

Режим принудительного отключения блока дедупликации (устанавливается битом `CTRL_REG[1]`).

* Все входящие 32-битные слова от датчика упаковываются строго в 5-байтовые **RAW-кадры** (`HEADER_RAW` + 4 байта данных) и транслируются в 8-битную шину AXI-Stream.
* Словарь, таблицы CMS и фильтры Блума замораживаются в текущем состоянии и не потребляют динамическую мощность.

---

### 8.8. Сравнительная характеристика алгоритмов передатчика

| Алгоритм (`ALGO_SEL`) | Эффективность ($C_r$) | Затраты LE | BRAM / LUTRAM | Макс. частота ($f_{\text{max}}$) |
| --- | --- | --- | --- | --- |
| **TinyLFU + CU-CMS** (`00`) | **Максимальная** | Средние (~1200 LE) | 2.4 КБ (1 M9K) | High (~100–120 МГц) |
| **Segmental LRU** (`01`) | Высокая | Низкие (~500 LE) | 1.3 КБ | Very High (~130–150 МГц) |
| **Clock / CAR** (`10`) | Средняя / Высокая | **Минимальные** (~200 LE) | 1.0 КБ | **Maximum** (>180 МГц) |
| **Pure LFU** (`11`) | Средняя | Низкие (~400 LE) | 1.1 КБ | High (~130 МГц) |

## 9. Система контроля целостности и обработки ошибок

### 9.1. Аппаратный обработчик ошибок (Fast-Path Hardware Error Handler)

Для исключения задержек программного отклика и предотвращения замусоривания словарей рассинхронизированными данными в RTL приемника интегрирован аппаратный FSM обработки ошибок:

```text
       Сбой CRC / Ошибка ключа на шине
                     │
                     ▼
  ┌─────────────────────────────────────┐
  │     ERROR_HANDLER (Fast Path)       │
  ├─────────────────────────────────────┤
  │ 1. Блокировка вывода (tvalid = 0)   │ (Такт N)
  │ 2. Сброс буфера валидации CRC       │ (Такт N)
  │ 3. Запрет записи в словарь RX       │ (Такт N)
  │ 4. Взвод линии прерывания rx_irq    │ (Такт N+1)
  └──────────────────┬──────────────────┘
                     │
                     ▼
        [ Программный уровень ЦПУ ]
         (Логирование и сбор статистики через iolink)

```

* **Изоляция:** При фиксации ошибки CRC или попытке извлечь несуществующий ключ аппаратная логика мгновенно обнуляет валидность кадра, предотвращая попадание мусора в ЦПУ.
* **Защита словаря:** Регистрация изменений в `dictionary[Key]` для сбойного пакета заблокирована.

---

### 9.2. Блочный контроль целостности (Block CRC & Receiver Validation Buffer)

Чтобы исключить 33% оверхед от добавления байта CRC в каждый короткий 2-байтовый кадр `KEY`, в системе реализован режим **Block CRC**:

```text
 Поток байт: [ KEY ] [ KEY ] [ RAW ] ... [ HEADER_CRC (0xD4) ] [ CRC8 ]
             └───────────────────────┘
            Буферизация в Validation FIFO

```

1. **Передатчик (`dedup_tx_top`):** Непрерывно вычисляет полином CRC-8 по всем передаваемым байтам. При возникновении паузы в FIFO или после передачи $M$ слов (задается в `CRC_CFG_REG[5:3]`) передатчик отправляет кадр `HEADER_CRC` (`0xD4`) + `CRC8`.
2. **Приемник (`dedup_rx_top`):** Восстановленные слова накапливаются в промежуточном **Буфере Валидации (Validation FIFO)**. Пропускание пачки слов к ЦПУ происходит единовременно только при успешном совпадении принятого CRC с вычисленным.
