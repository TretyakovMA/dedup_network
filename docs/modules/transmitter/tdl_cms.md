# tdl_cms

## Назначение

Реализует Count-Min Sketch для TinyLFU. Для двух хэш-адресов вычисляет оценку частоты после предполагаемого обновления, сохраняет подготовленные значения до `commit` и по отдельному запросу уменьшает все счётчики вдвое.

## Порты

| Порт | Направление | Ширина или тип | Назначение |
| --- | --- | --- | --- |
| `clk` | Вход | 1 | Общий такт TX. Обмен, commit и запрос aging фиксируются по положительному фронту. |
| `rst_n` | Вход | 1 | Общий сброс, активный низким уровнем. Отменяет подготовленную операцию и запускает очистку таблицы. |
| `req_valid` | Вход | 1 | TinyLFU запрашивает оценку для подходящего промаха. |
| `req_ready` | Выход | 1 | Можно принять запрос оценки. Снимается до завершения текущей операции и обслуживания. |
| `req_h0` | Вход | 8 | Адрес столбца в строке 0, полученный из `h_cms1`. |
| `req_h1` | Вход | 8 | Адрес столбца в строке 1, полученный из `h_cms2`. |
| `req_cu_disable` | Вход | 1 | 0 выбирает conservative update, 1 выбирает standard update. |
| `rsp_valid` | Выход | 1 | Предсказанная оценка готова. |
| `rsp_ready` | Вход | 1 | TinyLFU готов принять оценку. |
| `rsp_est` | Выход | 4 | `min(c0_next,c1_next)` после подготовленного обновления. |
| `commit` | Вход | 1 | Один импульс TinyLFU для записи подготовленных счётчиков после приёма оценки. |
| `aging_req` | Вход | 1 | Однотактный запрос деления всей таблицы между словами. Допускается на фронте commit или при свободном CMS. |
| `aging_done` | Выход | 1 | Однотактное подтверждение после завершения деления всей таблицы. |
| `busy` | Выход | 1 | Модуль очищает таблицу, выполняет оценку, ждёт commit или выполняет aging. |

## Логика работы

### Таблица и оценка

| Параметр структуры | Значение |
| --- | ---: |
| Глубина | 256 столбцов в каждой строке |
| Число строк / независимых счётчиков на оценку | 2 |
| Ширина счётчика | 4 бита |
| Диапазон | 0…15, saturating |
| Общий объём данных | 2 × 256 × 4 = 2048 бит (256 байт) |

`h_CMS1[7:0]` выбирает счётчик строки 0, `h_CMS2[7:0]` — строки 1. Поскольку обе строки имеют глубину 256, весь 8-битный диапазон индекса допустим.

После сброса оба банка очищаются до первого запроса. Значения CMS хранятся отдельно от содержимого и маски валидности словаря.

Для входа с адресами `a0=h_CMS1`, `a1=h_CMS2`:

```text
c0    = counters[0][a0]
c1    = counters[1][a1]
f_before = min(c0, c1)
```

Это оценка до обновления. Выход `rsp_est` выдаёт минимум подготовленных значений после обновления. Хэш-коллизии могут увеличить значения счётчиков из-за других слов. Минимум двух оценок ограничивает завышение, а насыщение удерживает счётчики в пределах 0…15.

### Conservative и standard update

#### Conservative Update (обычный режим)

После чтения `c0/c1` вычисляется `m=min(c0,c1)`. Увеличиваются только те выбранные ячейки, значение которых равно минимуму. Если оба равны минимуму, увеличиваются обе:

```text
if c0 == m: counters[0][a0] := min(c0 + 1, 15)
if c1 == m: counters[1][a1] := min(c1 + 1, 15)
```

#### Standard update (`CU_DISABLE=1`)

Смысл бита `MODE_REG[2]` — отключить Conservative Update и перейти на обычный режим CMS. Правило update — инкрементировать оба адресованных счётчика с насыщением независимо от их равенства:

```text
counters[0][a0] := min(c0 + 1, 15)
counters[1][a1] := min(c1 + 1, 15)
```

`f_est=min(c0_next,c1_next)` — предсказанная оценка **после** выбранного update. На response память ещё не изменена. Оба CU сравнения используют один m по старым c0/c1. Адреса и новые значения сохраняются до отдельного commit.

### Последовательность запроса, ответа и commit

TinyLFU обращается к CMS после промаха, который прошёл фильтр Блума, или при выключенном фильтре.

Адреса и режим захватываются при `req_valid && req_ready`. Источник удерживает поля запроса до этого фронта. CMS читает старые счётчики, вычисляет будущие значения и удерживает `rsp_valid` и `rsp_est` до `rsp_valid && rsp_ready`. Адреса и будущие значения остаются сохранёнными после приёма оценки. На отдельном более позднем фронте `commit` CMS запускает запись ровно один раз. Импульс без ожидающей подтверждения оценки считается нарушением протокола. TinyLFU посылает его только для слова, получившего оценку CMS, включая отказ вставки по частоте.

На фронте приёма запроса читаются оба адреса. На следующем фронте `rsp_valid` и `rsp_est` получают действительные значения. После приёма ответа на фронте `commit` оба банка одновременно записывают сохранённые значения.

В сбросе `req_ready`, `rsp_valid`, `busy` и `aging_done` равны нулю. Сброс удаляет ожидающие запись и обслуживание. После сброса первый запрос допустим, когда все счётчики логически равны нулю. TinyLFU держит свой `req_ready=0` до готовности CMS и завершения всех запущенных операций, включая деление локальных счётчиков и ротацию BF.

### Aging и очистка

`tdl_aging_ctrl` выдаёт `aging_req` по окончании обычных записей граничного слова. Сам CMS принимает запрос деления в простое или вместе с `commit`. В простое `aging_req` имеет приоритет над запросом оценки. При совпадении `aging_req` и `commit` оба счётчика сначала обновляются, а обход начинается со следующего такта. Каждая ячейка уменьшается вдвое с округлением вниз.

```text
counter := counter >> 1
```

RTL делит оба банка параллельно по одному адресу за два такта. Первый такт читает счётчики, второй записывает значения после сдвига. `aging_done` выставляется через 512 тактов после приёма `aging_req`, на фронте последней записи.

Каждая строка хранится в отдельном синхронном банке. После снятия сброса CMS очищает оба банка параллельно за 256 тактов и только затем поднимает `req_ready`.
